## Three integration surfaces (important framing)

| Surface | What it is | Control available |
|---|---|---|
| A. `@openai/codex-sdk` (what a2a-codex uses) | Spawns `codex exec --experimental-json` once per turn; parses JSONL events from stdout [verified: S2 index.js:172,250-261] | Start/resume thread, run turn, abort (kills process), structured output, local images. No approvals, no steering, no questions. |
| B. `codex app-server` (experimental, JSON-RPC 2.0 over stdio JSONL / unix socket / ws) | Long-lived process; threads and turns are first-class [verified: S3 `app-server --help`; S6] | Everything: `turn/steer`, `turn/interrupt`, server-initiated approval requests, `item/tool/requestUserInput`, MCP elicitation, auth login flows, thread resume/fork, token usage events. |
| C. `codex mcp-server` | Listed in 0.137.0 `--help` [verified: S3] but docs say the `codex mcp-server` command and `codex-mcp-server` binary "have been removed" and tell integrators to use the app server [verified: S7 via WebFetch]. Do not build on it. |

The SDK package page itself recommends the app server for custom clients that need "authentication, conversation history, approvals, and streamed agent events" [verified: S7].

## Details per dimension

### D1 Run lifecycle and event stream

SDK path (current wrapper): `thread.runStreamed(input, {signal, outputSchema})` returns `{events: AsyncGenerator<ThreadEvent>}` [verified: S2 index.d.ts]. Each call spawns `codex exec --experimental-json [resume <id>] ...`, writes the whole prompt to stdin and closes it, then streams JSONL stdout [verified: S2 index.js:172,250-261]. One process equals one turn. `thread.started` carries `thread_id`; `turn.started`; items go `item.started` -> `item.updated` -> `item.completed`; the turn ends with `turn.completed{usage}` or `turn.failed{error:{message}}`; fatal stream error is `{type:"error", message}` [verified: S2 index.d.ts ThreadEvent]. `agent_message` items arrive as growing snapshots (not deltas); the wrapper diffs them by item id [verified: S1 executor.ts:208-230]. Non-zero exit or signal makes the SDK generator throw (index.js ~288-291).

App-server path: `initialize` (clientInfo, capabilities) then `initialized`; `thread/start`, `turn/start{threadId,input[],...overrides}`; notifications `turn/started`, `item/started`, `item/agentMessage/delta`, `item/completed`, `turn/completed` (final `Turn.status`: `completed | interrupted | failed | inProgress`), `thread/status/changed` with `ThreadStatus` = `notLoaded | idle | systemError | active{activeFlags}` and flags `waitingOnApproval`, `waitingOnUserInput` [verified: S4 TurnStatus.ts, ThreadStatus.ts, ThreadActiveFlag.ts; S6]. `serverRequest/resolved {threadId, requestId}` confirms a server request was answered [verified: S4].

### D2 Abort / interrupt

SDK: abort signal is passed straight to `spawn` so aborting kills that turn's child process [verified: S2 index.js:250-252]. Scope: one turn (one process). What stays valid: the thread on disk, so `resumeThread(id)` works for the next turn [inferred from S2 resumeThread doc: "Threads are persisted in ~/.codex/sessions"]. Partial work (file edits already made) is not rolled back [inferred]. Wrapper: abort -> catches `AbortError` and leaves status publishing to `cancelTask`. Existing bug: `cancelTask` publishes `canceled` with `execution.contextId` as both taskId and contextId [verified: S1 executor.ts:320] (already known per design doc).

App-server: `turn/interrupt {threadId, turnId}` returns `{}` and the turn ends with `status: "interrupted"` [verified: S4 TurnInterruptParams.ts/Response; S6]. Thread remains loaded and usable [inferred]. Interrupt granularity is the turn, not the thread; a pending approval inside that turn is presumably cancelled (decision `cancel` exists for the same purpose) [inferred].

### D3 Steering

SDK: none. A caller message during a running turn cannot be injected; `runStreamed` input is fixed at spawn (stdin closed immediately) [verified: S2 index.js:260-261]. Workaround (provider-local): abort the turn, then `resumeThread(id).runStreamed(mergedPrompt)`; loses in-flight tool work and any partial reasoning [inferred]. Wrapper today simply serializes: a second message for the same context waits behind the running turn (queue semantics, not steering) [verified: S1 executor.ts:293-297].

App-server: native. `turn/steer {threadId, clientUserMessageId?, input: UserInput[], expectedTurnId}` -> `{turnId}`. `expectedTurnId` is a required precondition that must match the active turn. Fails if no turn is active. Does not emit `turn/started`; does not accept `model`, `cwd`, `sandboxPolicy`, `outputSchema`. Turns of kind `review` and `compact` are not steerable: error `activeTurnNotSteerable{turnKind}` [verified: S4 TurnSteerParams.ts, NonSteerableTurnKind.ts, CodexErrorInfo.ts; S6]. No mode flag (inject vs queue); steer is injection into the running turn. There is no native "queue for next turn" call: that is `turn/start` after completion [inferred]. 0.171.0 fixed a bug where edits made earlier in the turn were lost from aggregate diffs when steering [verified: S8].

### D4 Agent-initiated permission/approval requests

SDK: none surfaced. `codex exec` has no interactive approval channel; the wrapper rejects `approvalPolicy: "on-request"` at startup and defaults to `never` [verified: S1 executor.ts:385-390, defaults.ts:31, README.md:207,459]. With `never`, unapproved MCP tool calls fail with "MCP tool call requires approval, but approval policy is never" [verified: S1 README.md:364]. Out-of-band alternative available in exec mode: Codex config hooks with event `permissionRequest` (command hook) [verified: S4 HookEventName.ts exists; `exec --help` shows `--dangerously-bypass-hook-trust`]; that the hook can return allow/deny is [inferred].

App-server: server-to-client JSON-RPC requests (the client must reply with a JSON-RPC response using the request `id`):
- `item/commandExecution/requestApproval` params: `threadId, turnId, itemId, startedAtMs, approvalId?, reason?, networkApprovalContext?, command?, cwd?, commandActions?, proposedExecpolicyAmendment?, proposedNetworkPolicyAmendments?` (docs add `availableDecisions`); response `{decision}` with decision `accept | acceptForSession | {acceptWithExecpolicyAmendment:{execpolicy_amendment}} | {applyNetworkPolicyAmendment:{network_policy_amendment}} | decline | cancel` [verified: S4 CommandExecution*.ts; S6].
- `item/fileChange/requestApproval` params: `threadId, turnId, itemId, startedAtMs, reason?, grantRoot?`; decisions `accept | acceptForSession | decline | cancel` [verified: S4].
- `item/permissions/requestApproval` (for the built-in `request_permissions` tool): params include `permissions: RequestPermissionProfile`, `cwd`, `reason`; response `{permissions: GrantedPermissionProfile, scope: "turn" | "session", strictAutoReview?}` [verified: S4].
- `mcpServer/elicitation/request` (MCP tool approval prompts can arrive as elicitations, gated by `granular.mcp_elicitations`) [verified: S4 AskForApproval.ts, McpServerElicitationRequestParams.ts].
Option mapping to once/always/deny: `accept` = once, `acceptForSession` = always-for-session, `acceptWithExecpolicyAmendment` = always (persistent rule, Codex-side), `decline` = deny and let the agent continue, `cancel` = deny and interrupt the turn [mapping of `cancel` is inferred from name and docs ordering].
Async/out-of-band: the request is a pending JSON-RPC request inside the app-server process; the turn is blocked until the client responds, so a client can answer later (seconds, minutes) as long as the connection is alive. `thread/status/changed` shows `waitingOnApproval`. Timeout/default when unanswered: not found (no documented timeout). Docs state that for the managed human-command flow, pending prompts are replayed to a capable client that reconnects, and that if no capable connection exists the command is rejected [verified: S6 summary]. Sequence per docs: item started -> approval request -> client reply -> `serverRequest/resolved` -> `item/completed` with final status `completed | failed | declined` [verified: S6].
Reviewer routing: `approvalsReviewer: "user" | "auto_review" | "guardian_subagent"`; guardian events `item/autoApprovalReview/started|completed`, `guardianWarning` [verified: S4].

### D5 Agent-initiated questions

SDK: none. AS: `item/tool/requestUserInput` is EXPERIMENTAL; the docs describe 1-3 short questions per request. Shape: `questions: [{id, header, question, isOther (free text allowed), isSecret, options: [{label, description}] | null}]`; reply `{answers: {[questionId]: {answers: string[]}}}`; thread flag `waitingOnUserInput` [verified: S4; S6]. `options: null` means free text. Multi-select is not modeled (answers is an array but no `multiple` flag) [verified: S4 absence]. `mcpServer/elicitation/request` supports `mode: "form"` with `requestedSchema` (string/number/boolean/enum/multi-select primitives) or `mode: "url"` (`url`, `elicitationId`), reply action `accept | decline | cancel` [verified: S4 McpElicitation*.ts].

### D6 Auth-required flows

SDK: credentials come from `~/.codex` login state or the `CODEX_API_KEY` env var (`apiKey` option sets `env.CODEX_API_KEY`) [verified: S2 index.js ~line 245 area (`env.CODEX_API_KEY = args.apiKey`)]. If unauthenticated, exec fails; surfaced as `turn.failed`/`error` message string only [inferred]. The wrapper tells users to set `OPENAI_API_KEY` [verified: S1 client-factory.ts comment].

AS: structured. `account/read`, `account/login/start` variants (`apiKey`; `chatgpt` returns `loginId`+`authUrl`; `chatgptDeviceCode` returns `loginId`, `verificationUrl`, `userCode`; `chatgptAuthTokens` experimental, client supplies `accessToken`, `chatgptAccountId`), `account/login/cancel`, notifications `account/login/completed`, `account/updated`; server request `account/chatgptAuthTokens/refresh {reason:"unauthorized", previousAccountId}` which the client answers with fresh tokens within ~10 s; error info `unauthorized` [verified: S4; S6]. This maps naturally to `auth-required` (url + user code). MCP server OAuth: `mcpServer/oauth/login` and `mcpServer/oauthLogin/completed` [verified: S4 ClientRequest/ServerNotification lists].

### D7 Session persistence and resume

SDK: `Codex.resumeThread(id, opts)`: "Threads are persisted in ~/.codex/sessions" [verified: S2 index.d.ts]; resume passes `resume <threadId>` to exec (index.js ~224). a2a-codex keeps `contextId -> thread` only in memory and never calls `resumeThread`, so after a process restart the context starts a fresh thread (conversation history lost) [verified: S1 session-manager.ts, grep for resumeThread shows only the interface]. Persisting `contextId -> thread_id` in the core store would make this resumable [inferred]. Gotcha: thread options (sandbox, approval) must be re-supplied on resume [inferred; `resumeThread(id, options)` takes ThreadOptions].
AS: `thread/resume {threadId, ...overrides}` (by id, by history, or by path), `thread/fork`, `thread/list`, `thread/archive`; threads unload ~60 s after the last subscriber leaves (`thread/closed`) [verified: S4; S6]. Pending approval survival across a server restart: not documented; since a pending approval is an in-flight JSON-RPC request in a dead process, the turn is gone and the item is not resumed mid-turn [inferred]. Reconnect (same process) replay exists only for the managed human-command flow per docs [verified: S6].

### D8 Concurrency

SDK: any number of processes; wrapper chains turns per context via `session.executionQueue` [verified: S1 executor.ts:293]. Two simultaneous `resume` of the same thread id from separate processes would race on the session file [inferred].
AS: multiple threads per process; per-thread single active turn is implied by `turn/steer.expectedTurnId` and `turn/interrupt.turnId` [inferred]. Behavior of `turn/start` while a turn is active: not found (docs excerpt documents steer as the way to add input; `turn/start` with `toolOutput` queues if a turn is active per one doc mention) [verified: S6 partial]. Server overload error `-32001` with retry/backoff in WebSocket mode [verified: S6].

### D9 Tool, MCP, reasoning, plan, todo events

SDK items (exec JSON) [verified: S2 index.d.ts]: `command_execution{command, aggregated_output, exit_code?, status}`, `file_change{changes:[{path,kind:add|delete|update}], status}`, `mcp_tool_call{server, tool, arguments, result?, error?, status}`, `agent_message`, `reasoning{text}` (summary), `web_search{query}`, `todo_list{items:[{text,completed}]}`, `error`. Wrapper maps them to sideband events and only emits file path+kind and sanitized output [verified: S1 event-mapper.ts].
AS adds structured deltas (`item/agentMessage/delta`, `item/reasoning/summaryTextDelta|textDelta`, `item/commandExecution/outputDelta`, `item/fileChange/outputDelta`, `item/fileChange/patchUpdated`, `item/mcpToolCall/progress`), `item/plan/delta` and `turn/plan/updated {explanation, plan:[TurnPlanStep]}`, `turn/diff/updated {diff}`, sub-agent items `collabAgentToolCall` (senderThreadId/receiverThreadIds), dynamic tool calls (`item/tool/call` server request: the client can implement tools) [verified: S4].

### D10 Input modalities and outputs

SDK `Input = string | UserInput[]` with `{type:"text"}` and `{type:"local_image", path}`; text parts are joined with blank lines and images become repeated `--image <path>` flags; remote/base64 images are not supported, so core would have to write bytes to a temp file [verified: S2 index.js normalizeInput, index.js:228]. No generic file input (only by path mention in text) [inferred]. Structured output: `TurnOptions.outputSchema` written to a temp file and passed as `--output-schema` [verified: S2 index.js:202]. Final answer text is `agent_message` text (JSON when schema given). File changes: `file_change` has only paths/kinds, no diff (SDK); AS has `turn/diff/updated` unified diff [verified: S4; S6]. Wrapper does not wire `outputSchema` or images today [verified: S1 executor.ts calls `runStreamed(promptText, {signal})` only].

### D11 Usage, cost, context

SDK: only at `turn.completed`: `Usage{input_tokens, cached_input_tokens, output_tokens, reasoning_output_tokens}`; wrapper maps them to `UsageCallRecord` with cost null [verified: S1 executor.ts:51-70]. No cost, no context window size, no per-LLM-call breakdown. AS: `thread/tokenUsage/updated` -> `ThreadTokenUsage{total, last: TokenUsageBreakdown, modelContextWindow}`, `account/rateLimits/updated`, `thread/compacted`/`contextCompaction` items [verified: S4].

### D12 Approval policy configuration

Verified values: `ApprovalMode = "never" | "on-request" | "on-failure" | "untrusted"` (SDK, passed as `--config approval_policy="..."`); `SandboxMode = read-only | workspace-write | danger-full-access`; `--add-dir`; `networkAccessEnabled` and `webSearchMode: disabled|cached|live` [verified: S2 index.d.ts, index.js:188-221]. AS adds `AskForApproval` variant `granular{sandbox_approval, rules, skill_approval, request_permissions, mcp_elicitations}`, `approvalsReviewer`, per-turn overrides in `turn/start`, permission profiles (`permissionProfile/list`), saved rules via execpolicy amendments [verified: S4]. Allow-lists: execpolicy `.rules` files (`--ignore-rules` flag exists) and MCP `default_tools_approval_mode` / `tools.<tool>.approval_mode` [verified: S3 `exec --help`; S1 types.ts:189-225]. Important: no mode lets exec ask a human; `on-request` in exec has no channel, so the wrapper bans it [verified: S1].

### D13 Hooks / lifecycle callbacks

No in-process callbacks in the SDK. Codex config hooks (command-based) are the extension point: events `preToolUse`, `permissionRequest`, `postToolUse`, `preCompact`, `postCompact`, `sessionStart`, `userPromptSubmit`, `subagentStart`, `subagentStop`, `stop` [verified: S4 HookEventName.ts]; AS reports `hook/started`/`hook/completed` for synchronous hooks (S6). Hooks are trust-gated (`--dangerously-bypass-hook-trust` in exec) [verified: S3]. SDK lifecycle callbacks of the form `onSomething(fn)`: not found. The wrapper's own lifecycle is derived from events.

### D14 Stability, versioning, license, spawn

- Installed SDK and CLI 0.137.0; latest on npm 0.171.0 (34 minor versions newer) [verified: S2, S3, S5]. The wrapper pin `^0.137.0` is a 0.x caret, i.e. `>=0.137.0 <0.138.0`, so a fresh install will never receive 0.171 without a manual bump [inferred from semver rules for 0.x].
- SDK source on main adds `threadSource` to `ThreadOptions`; otherwise the same option set [verified: S9]. Release notes 0.170/0.171 list no SDK changes and no labeled breaking changes; legacy sandbox policy code removed internally [verified: S8 summary].
- The SDK drives the CLI via the explicitly named `--experimental-json` flag, so the JSONL event schema is not a stable contract [verified: S2 index.js:172; inferred stability implication].
- App-server: `[experimental]` in `--help`; WebSocket transport "experimental and unsupported"; `experimentalApi` capability gates fields; methods have been removed (`thread/rollback` removed, replaced by `thread/revert`) [verified: S3, S6].
- License Apache-2.0 [verified: S2 package.json]. Spawn: SDK uses Node `child_process.spawn` of the platform binary from optional dependency `@openai/codex-<platform>` or `codexPathOverride`; env is inherited from `process.env` unless `env` option is given; adds an originator env var [verified: S2 index.js:137-260]. A native Windows binary exists (win32-x64) [verified: S3].

## Gaps and surprises

1. The current SDK surface (what a2a-codex uses) exposes none of approvals, questions, steering, or auth flows. These exist only in the app-server protocol. A provider that wants `run.ask`, `onMessage`, or structured auth-required must either move to app-server (new process model: long-lived JSON-RPC process, not per-turn spawn) or run without them.
2. The app-server is experimental, and the questions API is marked EXPERIMENTAL even inside it; field renames are expected. Generated TypeScript bindings via `codex app-server generate-ts` are version-matched and could be vendored/pinned.
3. `codex mcp-server` (once the way to get approval elicitations over MCP) is documented as removed; do not plan on it.
4. a2a-codex never calls `resumeThread`, so conversation continuity does not survive a restart even though Codex persists threads.
5. Wrapper bug already on the migration list: `cancelTask` publishes with `contextId` as `taskId` (executor.ts:320).
6. The SDK's `Thread` object is stateful only for `threadId`; options are per thread object, not per turn (AS `turn/start` supports per-turn overrides).
7. `todo_list` and `reasoning` items are summaries; raw reasoning is deliberately not surfaced by the wrapper (privacy rule in event-mapper).
8. "Cancel" semantic in approvals: `cancel` decision likely interrupts the turn, whereas `decline` lets the agent continue. A neutral `deny` option needs a "deny and abort" variant for providers that have it [inferred].
9. 0.x pin means a surprise-free but stale dependency; tests against 0.171 are needed before any move.

## Implications for a provider-neutral contract

- `run.ask` for permission: a Codex provider backed by app-server translates `item/*/requestApproval` into `CoreInteraction{kind:"permission", action, target, options}`. Options needed: `once`, `session` (acceptForSession; scoped narrower than "always"), `always` (execpolicy amendment, persistent), `deny`, and `deny_and_abort` (cancel). Core `PermissionOption` should therefore carry an open `id` plus a `scope: "once" | "turn" | "session" | "persistent"` and a flag `abortsRun`, not just once/always/deny.
- Provider-side payload to preserve in `detail`/`meta`: `itemId`, `approvalId`, `reason`, `command`, `cwd`, proposed amendments (opaque), because the reply must echo structured objects (`acceptWithExecpolicyAmendment`).
- Asynchrony: the request id lives in the app-server process; a reply is valid only while that process and turn are alive. `resume?(state)` for a pending permission cannot be honored across a restart for Codex; core should be able to ask the provider "can you resume a pending interaction?" by the presence of the handler, and the Codex provider would fail the turn with a precise reason (restart lost approval) instead.
- Questions: `item/tool/requestUserInput` maps to `CoreInteraction{kind:"question"}` with a list of questions (each: id, header, prompt, options, allowFreeText=`isOther`, secret=`isSecret`). So `question` should be an array of sub-questions with ids and a `secret` flag, and answers are `{[id]: string[]}`. `mcpServer/elicitation/request` needs the JSON-schema form variant and a URL variant (auth/consent link).
- Auth: Codex's `chatgpt`/`chatgptDeviceCode` login gives `{url, userCode}`; `CoreInteraction{kind:"auth"}` should allow `url` + `code` + `expiresIn`-like detail and a completion signal (`account/login/completed`), and the result "completed" must be producible by the provider without a caller message (out-of-band completion).
- Steering: provider `onMessage(run, message)` for Codex-on-app-server is a direct `turn/steer` with `expectedTurnId` (core must give the provider the current turn identity or let it track it). Outcomes `accepted` (steered) and `rejected` (e.g. `activeTurnNotSteerable`, no active turn) map cleanly; there is no native `queued`. For Codex-on-SDK, `onMessage` workaround = abort + `resumeThread` with merged prompt, which should return `accepted` only after the new turn started; document that in-flight tool work is lost. Core's default (queue as next turn) is exactly what the current wrapper does via `executionQueue`; that serialization should move to core so providers do not each implement it.
- Abort: `abortBackend(runInfo)` needs `{taskId, contextId, providerSessionId (thread id), providerTurnId}`; on SDK it is `AbortController.abort()`, on AS it is `turn/interrupt`. `abortOrphan` for Codex: after restart there is no live process, so nothing to stop; with AS surviving as a daemon (`app-server daemon`) an orphan turn could still run, so `abortOrphan` would be `thread/loaded/list` + `turn/interrupt` [inferred].
- Resume: provider must persist `contextId -> thread_id`; `resume?` for conversation continuity is `resumeThread(id)` / `thread/resume`. Core's store should reserve a provider-opaque `ResumeState` blob (thread id, last turn id, options).
- Events: Codex needs core's event vocabulary to include `plan/todo` (list of steps with status), `file_change` (path, kind, optional diff), `usage` (input/output/cached/reasoning, optional cost, optional context window), `tool_call` (kind shell/mcp/web_search/subagent), `reasoning` (summary only). Cost and context window are optional.
- Input: `CorePart` file/image parts must be materialized to local paths for Codex (`--image` / `localImage`), a provider-local workaround (write bytes to a temp file, clean up after the turn).
- Structured output: `outputSchema` passes through; core should carry a request-level `responseSchema?`.
- Capability signalling by handler presence works for Codex: SDK-based provider implements `abortBackend` only; AS-based provider additionally implements `onMessage` and an `ask` bridge. The two cannot coexist in one process model without switching to AS.
