## 3. Details per dimension

### D1 Run lifecycle and event stream

- Entry point: `query({prompt, options}): Query` where `Query extends AsyncGenerator<SDKMessage, void>` [verified: SDK.d.ts:2844, 3244]. `prompt` is `string | AsyncIterable<SDKUserMessage>`.
- `SDKMessage` is a union of ~40 members [verified: SDK.d.ts:5292]. Ones that matter for a task runner: `assistant`, `user`, `user` replay, `result`, `system` (subtypes include `init`, `session_state_changed`, `permission_denied`, `notification`, `hook_started/progress/response`, `plugin_install`, `compact_boundary`, `status`, `task_*`, `background_tasks_changed`, `model_refusal_fallback`, `model_refusal_no_fallback`), `stream_event`, `tool_progress`, `auth_status`, `rate_limit_event`, `api_retry`, `tool_use_summary`, `elicitation_complete`, `prompt_suggestion`.
- First message is `system/init` carrying `session_id`, `model`, `cwd`, `tools`, `mcp_servers[{name,status}]`, `plugins`, `permissionMode`, `claude_code_version`, `apiKeySource`, `capabilities` [verified: SDK.d.ts:5864-5935]. Emitted before any model call, so a probe is free [verified: W/executor.ts:181-183 comment; [inferred] correct].
- Exactly one `result` message per turn "after that turn's assistant, user and stream_event messages; treat it as the turn-complete signal" [verified: SDK.d.ts:5686-5689 doc comment]. Informational system messages may follow it.
- Result subtypes: `success` | `error_during_execution` | `error_max_turns` | `error_max_budget_usd` | `error_max_structured_output_retries` [verified: SDK.d.ts:5660ish SDKResultError]. Additionally `terminal_reason` of `blocking_limit, rapid_refill_breaker, prompt_too_long, image_error, model_error, api_error, malformed_tool_use_exhausted, aborted_streaming, aborted_tools, stop_hook_prevented, hook_stopped, tool_deferred, max_turns, background_requested, completed, budget_exhausted, structured_output_retry_exhausted, tool_deferred_unavailable, turn_setup_failed` [verified: SDK.d.ts:9636]. `queued_turn_count` on the result says more turns follow without further input [verified: SDK.d.ts:5653].
- Error-type taxonomy at message level: `SDKAssistantMessage.error?: 'authentication_failed'|'oauth_org_not_allowed'|'account_on_hold'|'verification_required'|'billing_error'|'rate_limit'|'overloaded'|'invalid_request'|'model_not_found'|'server_error'|'unknown'|'max_output_tokens'|'cloud_credential_error'` [verified: SDK.d.ts:3690]. Startup failure reasons on the zeroed error result: `startup_failure_reason` [verified: SDK.d.ts:5800ish SDKStartupFailureReason].
- In streaming-input mode the process stays alive after a result; the wrapper must end the input stream or the CLI keeps running [verified: W/executor.ts:334-336, 493-496]. After an error result in streaming mode the TS loop "yields that result and then throws" if the last response is an error [verified: streaming-vs-single-mode doc].
- Wrapper: maps `init` -> `agent_started`, `permission_denied` -> sideband `decision`, assistant/user blocks to sideband events, `result` to usage + terminal status. It publishes A2A `working` -> `completed|failed` directly [verified: W/executor.ts:408, 394-404, 529; W/event-mapper.ts:96-190]. It never publishes `input-required` or `auth-required` [verified: grep of executor.ts, only states used are submitted/working/completed/failed/canceled].
- Held-open task: when background tasks (`background_tasks_changed`) are live after a result, the wrapper keeps the A2A task `working` for later rounds, one artifact per round [verified: W/executor.ts:490-516].

### D2 Abort and interrupt

- `options.abortController`: "When aborted, the query will stop and clean up resources" [verified: SDK.d.ts:1520-1524]. The wrapper treats abort as the thing that actually stops the subprocess [verified: W/executor.ts:339-347 comment].
- `Query.interrupt(): Promise<SDKControlInterruptResponse|undefined>` stops the current turn and keeps the session; only in streaming-input mode [verified: SDK.d.ts:2844-2858 "supported when streaming input/output is used"]. Result: the interrupted turn ends with an `error_during_execution` result, messages queued before the interrupt "still reach Claude once the interrupted response ends" [verified: streaming-vs-single-mode doc]. With capability `interrupt_receipt_v1` the response lists `still_queued` uuids; with `interrupt_cancel_queued_v1` the request can carry `cancel_queued:true` to also cancel queued/pending messages (response `cancelled`) [verified: SDK.d.ts:4570-4584, 5933]. `cancel_async_message` control request cancels one queued uuid [verified: SDK.d.ts:3877]. (The public `Query` method exposes `interrupt()` with no args in 0.3.286; `cancel_queued` is shown on the control-request type, [inferred] reachable only if the SDK Query surface exposes it; not verified.)
- `Query.close()` ends the session: "After calling close(), no further messages will be received" [verified: SDK.d.ts:3239-3241]. `Query.stopTask(taskId)` stops a background task, emits `task_notification` status `stopped` [verified: SDK.d.ts:3213-3217].
- What stays valid after abort: the session id and its persisted transcript (`persistSession`), so `resume: sessionId` works for the next prompt. The wrapper relies on this: "Continuity comes from the contextId -> Claude session mapping, which survives a failed task" [verified: W/executor.ts:355-360].
- The wrapper's cancel: `abortController.abort()` then `query.interrupt().catch(()=>{})`, publishes `canceled` itself [verified: W/executor.ts:644-660]. There is no separate "orphan" abort: if no execution is tracked in the in-memory `SessionManager`, `cancelTask` returns without doing anything [verified: W/executor.ts:647-651]. A claude subprocess with no live run in this process cannot exist after a restart (it dies with the parent) [inferred], so `abortOrphan` is effectively a no-op for Claude.
- Quirk: abort can end the iterator cleanly (no throw) or throw an error whose text includes "abort"; the wrapper handles both [verified: W/executor.ts:535-575, 603-605].

### D3 Steering (most design-relevant)

- Mechanism: streaming input. Pass an `AsyncIterable<SDKUserMessage>` as `prompt` and keep yielding, or call `Query.streamInput(stream)` [verified: SDK.d.ts:3212; docs]. Shape: `{type:'user', message: MessageParam, parent_tool_use_id: string|null, uuid?, priority?: 'now'|'next'|'later', shouldQuery?: boolean, origin?, timestamp?}` [verified: SDK.d.ts:6179-6230].
- Documented semantics: "A message you send during tool calls reaches Claude after those tool calls finish. Claude then answers it and your earlier message in one response. If the turn ends first, Claude starts a new turn for it." and "To choose when Claude reads a message you push during a response, set the message's `priority` field" [verified: streaming-vs-single-mode doc]. Type-level confirmation: result `user_message_uuids` = "any queued user message folded into the running turn between tool rounds"; `queued_turn_count` for sends still waiting [verified: SDK.d.ts:5653, 5667]. This is injection at the tool-round boundary, not mid-token.
- `priority` values `now|next|later` are typed but their exact semantics are not defined in the .d.ts or the fetched doc page [not found]. [inferred] from the `Notification` message enum and queue wording: `now` interrupts/injects earliest, `later` waits for turn end; must be verified by experiment before relying on it. A different CLI-internal queue exists with `immediate|high|medium|low` for notifications [verified: SDK.d.ts:5432], not necessarily the same.
- `shouldQuery:false` appends a message to the transcript without starting a turn; it merges into the next query [verified: SDK.d.ts:6216-6218].
- Abort-and-redirect (the generic workaround) is native here: `interrupt()` then yield the merged/new message; the session and context are preserved [verified: streaming doc].
- Correlation: stamp each sent message with a `uuid`; results/assistant messages echo `user_message_uuid`/`user_message_uuids` so core can tell which steering messages were absorbed into which turn [verified: SDK.d.ts:5663-5667, 3622].
- What a2a-claude does today: yields exactly one message then parks on a promise (`promptStream`), purely to keep the CLI alive for background-task wakeups. It never forwards a second caller message into the running query [verified: W/prompt-builder.ts:230-236, W/executor.ts:417]. A second A2A message to the same context is serialized behind the first via `session.executionQueue` (new SDK query with `resume`) [verified: W/executor.ts:631-632].
- Constraint: the single-string prompt mode closes stdin after the first result and cannot accept steering; streaming input is required for steering, `interrupt()`, `setPermissionMode()` and `canUseTool`-with-deferred flows [verified: SDK.d.ts:2844-2865; W/client-factory.ts:193-195].
- Support: partial-native. Native queue + fold-in-between-tool-rounds; the `now` semantics unverified; true mid-tool-call preemption only via `interrupt()`.

### D4 Agent-initiated permission requests

- Callback: `options.canUseTool?: CanUseTool` [verified: SDK.d.ts:1587]. Signature `(toolName: string, input: Record<string, unknown>, options) => Promise<PermissionResult | null>` [verified: SDK.d.ts:213-301].
- `options` fields: `signal: AbortSignal`, `suggestions?: PermissionUpdate[]`, `blockedPath?`, `mcpServer?:{name,source}`, `decisionReason?`, `title?` (full prompt sentence), `displayName?`, `description?`, `defaultToNo?`, `suppressAlwaysAllowRule?`, `toolUseID`, `agentID?`, `requestId`, `matchedAskRule?` [verified: SDK.d.ts:213-301].
- Result: `{behavior:'allow', updatedInput?, updatedPermissions?: PermissionUpdate[], toolUseID?, decisionClassification?}` or `{behavior:'deny', message: string, interrupt?: boolean, ...}` [verified: SDK.d.ts:2505-2518]. `updatedPermissions` entries: `addRules|replaceRules|removeRules|setMode|addDirectories|removeDirectories`, destination `userSettings|projectSettings|localSettings|session|cliArg` [verified: SDK.d.ts:2522-2560]. `interrupt:true` on deny stops the whole turn ([inferred] from name; semantics not documented in the .d.ts).
- Pending is unbounded and can be answered asynchronously: "The callback can stay pending indefinitely. Execution remains paused until your callback returns." [verified: user-input doc]; and in the d.ts: "permission prompts have no park deadline" [verified: SDK.d.ts:210-211]. Out-of-band answer: return `null` after sending the control_response yourself, echoing `requestId` [verified: SDK.d.ts:205-211]. Fail-closed: an accidental `null` leaves the tool blocked forever.
- Cancel while pending: the `signal` in `options` fires when the operation should abort [verified: SDK.d.ts:215-216]; a `control_cancel_request` exists on the protocol [verified: SDK.d.ts:3884]. [inferred] core's `outcome:'canceled'` maps to resolving with `{behavior:'deny', message:'canceled', interrupt:true}` plus aborting.
- Introspection: on an `initialize` response, `pending_permission_requests` lists unresolved `can_use_tool` requests; `session_state_changed` with `state:'requires_action'` signals the CLI is holding a prompt [verified: SDK.d.ts:390, 5816-5822]. So a `requires_action` system message is a ready-made signal for `input-required`.
- Policy that runs before the callback: deny rules, permission mode, allow rules, then the callback; "in some configurations, such as dontAsk mode, Claude Code doesn't call it" [verified: user-input doc]. Without any prompt surface (no `canUseTool`) an "ask" decision is terminal denial; surfaced as `system/permission_denied` with `tool_name, tool_use_id, decision_reason_type, decision_reason, message`, and authoritatively in `result.permission_denials[]` [verified: SDK.d.ts:5467-5500, 5640ish].
- Alternative: `permissionPromptToolName` routes prompts to an MCP tool [verified: SDK.d.ts:2005-2009]; `permissionPrompts:'none'` makes anything that would prompt an immediate deny [verified: SDK.d.ts:2010-2016].
- Hooks: `PreToolUse` output `{hookEventName:'PreToolUse', permissionDecision?: 'allow'|'deny'|'ask'|'defer', permissionDecisionReason?, updatedInput?, additionalContext?}` [verified: SDK.d.ts:2746-2752, 982]. `defer` is the documented way to stop and resume later: "register a PreToolUse hook that returns the defer decision instead of waiting in the callback, so the process can exit and resume later from the persisted session" [verified: user-input doc]; terminal reasons `tool_deferred` / `tool_deferred_unavailable` exist [verified: SDK.d.ts:9636]. `PermissionRequest` hook (input `tool_name, tool_input, permission_suggestions`; output `decision:{behavior:'allow',updatedInput?,updatedPermissions?} | {behavior:'deny',message?,interrupt?}`) fires when a prompt would be shown and can be used to notify or auto-answer [verified: SDK.d.ts:2491-2503].
- Wrapper today: does not set `canUseTool`, `hooks` or `permissionPromptToolName`; refuses interactive modes at startup: only `acceptEdits, dontAsk, plan, bypassPermissions` allowed, `default` (and `auto`) rejected as "requires an interactive approver" [verified: W/executor.ts:58, 734-740, W/capabilities.ts: `approvals: "headless"`]. In those modes an un-pre-approved tool is auto-denied and only visible as a sideband `permission_denied` decision event [verified: W/event-mapper.ts:181-186].
- Support: native.

### D5 Agent-initiated questions

- Tool: `AskUserQuestion`, ordinary tool_use block in an `assistant` message; routed to `canUseTool` with `toolName==='AskUserQuestion'` [verified: user-input doc; SDK-TOOLS.d.ts:31, 76].
- Input [verified: SDK-TOOLS.d.ts:1115-]: `questions` 1..4 items, each `{question: string, header: string (max 12 chars), options: 2..4 of {label: string, description: string, preview?: string}, multiSelect: boolean}`. No free-text question type; the UI adds an "Other" and the answer value carries the free text [verified: user-input doc "Support free-text input"; schema comment "no 'Other' option, that will be provided automatically"].
- Output [verified: SDK-TOOLS.d.ts:3768-3945; user-input doc]: allow with `updatedInput:{questions, answers:{[questionText]: string}, annotations?:{[questionText]:{preview?, notes?}}, response?}`. Multi-select: labels joined with ", " (d.ts says comma-separated string; doc also allows an array); `response` = freeform reply that replaces the structured answers. The original `questions` array must be passed back.
- `toolConfig.askUserQuestion.previewFormat: 'markdown'|'html'` enables `preview` content [verified: user-input doc; SDK.d.ts:1697-1702].
- Limits: not available inside subagents; if `tools` is set it must include `AskUserQuestion` [verified: user-input doc].
- Also: MCP servers can ask via elicitation: `options.onElicitation(request:{serverName, message, mode?:'form'|'url', url?, elicitationId?, requestedSchema?: JSON Schema, title?...}, {signal, requestId}) => Promise<ElicitResult|null>`; if no callback, requests not handled by hooks are declined automatically [verified: SDK.d.ts:716-735, 1483-1495, 1739-1749]. `Elicitation` and `ElicitationResult` hooks exist [verified: SDK.d.ts:957]. `onUserDialog` handles `request_user_dialog` control requests with per-`dialogKind` payloads; unanswered ones are bounded by a CLI park deadline [verified: SDK.d.ts:1750-1780].
- Wrapper: none wired (no `canUseTool`, `onElicitation`, `onUserDialog`). If the model calls AskUserQuestion in a headless mode, nothing answers it [inferred: no handler; behaviour of the CLI in that case (error tool_result vs denial) not verified].
- Support: native. Maps cleanly onto core `question` with `choices` and `multi` per question; note the multi-question (1..4) batch and per-option `description` have no counterpart in the sketch `CoreInteraction.question` (single prompt) so a provider would either emit up to 4 `ask()` calls or core's type needs `questions[]`.

### D6 Auth-required flows

- Login state is owned by the CLI: OAuth login (`/login`), `ANTHROPIC_API_KEY`, Bedrock/Vertex/Foundry env, `apiKeyHelper`; `init.apiKeySource` reports which [verified: SDK.d.ts:5868-5871]. The wrapper only warns if `ANTHROPIC_API_KEY` is unset [verified: W/executor.ts:110-115].
- Signals that a caller must act: assistant `error: 'authentication_failed' | 'oauth_org_not_allowed' | 'account_on_hold' | 'verification_required' | 'billing_error' | 'cloud_credential_error'` [verified: SDK.d.ts:3690]; `rate_limit` info `errorCode:'credits_required'`, `canUserPurchaseCredits` [verified: SDK.d.ts:5617-5619]; `SDKAuthStatusMessage {type:'auth_status', isAuthenticating, output[], error?}` [verified: SDK.d.ts:3692-3699]; startup failures `gateway_signin_required, gateway_access_denied, org_verify_failed, org_pin_mismatch...` [verified: SDK.d.ts:5836ish].
- MCP OAuth: server status `'connected'|'failed'|'needs-auth'|'pending'|'disabled'` in `Query.mcpServerStatus()` and `init.mcp_servers[].status` [verified: SDK.d.ts:1239, 3021]; `Query.reconnectMcpServer(name)` retries after auth is done elsewhere [verified: SDK.d.ts:3155]. URL-mode elicitation (`mode:'url'`, `url`, `elicitationId`) is how an MCP server asks the host to open a browser for auth, with `system/elicitation_complete` when done [verified: SDK.d.ts:716-725, 5112].
- No SDK-level "please log in, here is the URL" request for Claude's own account. [inferred] core `auth` interaction for Claude would be provider-synthesized: (a) MCP `needs-auth` / URL-mode elicitation -> `{kind:'auth', service: serverName, url}`; (b) account errors -> terminal `failed` with a reason (auth-required cannot be satisfied in-band because there is no resume-after-login within the run), unless core allows a retry of the same task after the operator logs in.
- Support: partial.

### D7 Session persistence and resume

- Options: `persistSession` (wrapper hard-sets true), `resume: <sessionId>`, `continue` (most recent in cwd, exclusive with resume), `forkSession`, `sessionId` (custom UUID; with resume only if forkSession), `resumeSessionAt` (truncate at a message UUID), `resumeDropsTurn` validation [verified: SDK.d.ts:1592, 1707, 1815, 2085-2130; W/client-factory.ts:171-174].
- Transcripts are JSONL files on local disk. ## 4. Gaps and surprises

1. The wrapper uses almost none of the interactive surface: `canUseTool`, `hooks`, `onElicitation`, `onUserDialog`, `Query.setPermissionMode`, `streamInput`, `priority`, `uuid`, `forkSession`, `resumeSessionAt`, `rewindFiles`, `getSessionMessages`, `toolConfig` are all unused [verified: grep of W/ non-test sources]. `approvals: "headless"` capability and the startup guard rejecting `default`/`auto` permission modes are the deliberate current stance [verified: W/executor.ts:734-740, W/capabilities.ts].
2. Claude's native model is a **single long-lived session/process with an in-band queue**, not task-per-turn. Core's `TaskRun`/`inbox`/`ask` fits it better than the one-shot "run -> done" shape, but the current wrapper starts a new `query()` per A2A task and holds the process open only for background-task wakeups (`inputClosed` deferred).
3. `AskUserQuestion` is not a separate callback: it is multiplexed through `canUseTool` and is answered by `allow + updatedInput.answers`. A permission-only handler that does `allow/deny` on `toolName` would mishandle questions (it would "allow" with the original input and no `answers`).
4. A deny result is *model-visible feedback*: `message` goes back to Claude, which then adapts. That is a richer outcome than a boolean: core's `declined` should be able to carry a caller message that the provider passes as `message` (this is also how "suggest an alternative" works).
5. Allow can mutate input (`updatedInput`) and persist rules (`updatedPermissions` writing settings files). A provider-neutral `PermissionOption` set (allow once / allow always / deny) must decide what "always" means; honoring it writes to `.claude/settings.local.json` (or session only). `suppressAlwaysAllowRule` and `defaultToNo` hints are given per request.
6. `priority` semantics (`now|next|later`) are typed but not defined in what I could read; do not hard-code expectations without an experiment.
7. Result `total_cost_usd`/`modelUsage` are cumulative in streaming sessions while `usage` is per-turn; the wrapper's `claudeUsageToCallRecord` stores `total_cost_usd` on every round, which double counts for held-open tasks [inferred].
8. The wrapper's own `cancelTask` early-returns when no execution is tracked, and `execute` ignores any caller message arriving while a task is running (it queues a new query). Nothing handles `input-required` replies, which would arrive as a new message on the same task/context.
9. The installed SDK (0.3.286) is 43 releases behind npm latest (0.3.329); anything in this report may differ in 0.3.329. I did not diff types.
10. Not found: any documented statement of what the CLI does when `AskUserQuestion` is called with no `canUseTool` in headless mode; details of resuming a `defer`red tool call.

## 5. Implications for a provider-neutral contract

**`run.ask` / permission and question (what a Claude `ProviderExecutor` has to do)**
- Install `options.canUseTool` once per `query()`; inside it branch on `toolName`:
  - `AskUserQuestion` -> build `CoreInteraction`(s) of kind `question` from `input.questions` (`question`->`prompt`, `options[].label/description`->`choices`, `multiSelect`->`multi`, `header`->a short title) and translate the result into `{behavior:'allow', updatedInput:{questions: input.questions, answers: {[questionText]: label | "a, b"}}}`. The core type should allow a batch of 1..4 questions (or the provider issues sequential asks and merges, which loses the single UI card). Free-text answers go in `answers[question]` as-is.
  - everything else -> `kind:'permission'` with `action = toolName`, `target` from `input` (`file_path`, `command`...) or `blockedPath`, display text from `title`/`description`/`decisionReason`, `options` allow once / allow always (only if `suggestions` present and not `suppressAlwaysAllowRule`) / deny, `detail` = `{toolUseID, agentID, mcpServer, decisionReason}`. Result mapping: answered+allow -> `{behavior:'allow', updatedInput: input, updatedPermissions?: suggestions}`; declined -> `{behavior:'deny', message: callerText ?? 'declined', interrupt?}`; `timeout`/`canceled` -> deny with a message (+ abort when canceled).
- `canUseTool` may stay pending indefinitely, so core's timeout policy (not the SDK's) is what bounds it; the `signal` in options is the cancel hook to resolve `ask` as `canceled`.
- Risk labels (`risk?: low|medium|high`) have no native source; `decisionReason`/`decisionClassification` and tool name are the only inputs. Leave to core's auto-answer rules (operator policy) keyed on tool name and `target`, not provider.
- Provider must also (a) stop rejecting `default`/`auto` permission modes when an `ask` path exists, (b) pass `AskUserQuestion` in `tools` if `tools` is restricted, (c) keep streaming-input mode on for the whole run (required by canUseTool-with-interrupt and setPermissionMode).
- `requires_action` `session_state_changed` message can drive the A2A `input-required` transition timing; `permission_denied` messages remain observability only.

**Steering (`inbox` / `onMessage`)**
- Claude can implement `onMessage` natively: push an `SDKUserMessage` (with `uuid`, optional `priority`) into the same input generator the run created, return `queued` or `accepted`. Correlate through `user_message_uuids` on the next assistant/result message: if the uuid appears in the *current* turn's `user_message_uuids`, it was folded in (`accepted`), if it starts a new turn, `queued`. This needs the input stream to be a controllable queue rather than the current "yield one then park" generator.
- The stronger "redirect now" variant is `interrupt()` then send; it ends the current turn with an `error_during_execution` result which the provider must NOT report as task failure (it must swallow that result like the abort case). Session context is retained. If `still_queued` is returned, decide whether to keep them.
- Provider-local detail core must not need to know: whether the result of the current turn is a steered one or a normal one, and how many results one A2A task spans (the wrapper already supports multiple results per task via the held-open rounds).

**Abort**
- `abortBackend(run)`: `abortController.abort()` + `query.interrupt()` (best effort) + resolve the input stream; this is what the wrapper does. Must also resolve any pending `canUseTool` promise (deny) so the subprocess is not blocked.
- `abortOrphan`: no-op for Claude in practice (subprocess dies with the host); only the persisted session remains, and that can be left for resume.

**Resume**
- `resume(state)` for Claude = start a new `query()` with `options.resume = sessionId` (and optionally `resumeSessionAt` to cut an interrupted turn). The only durable state is the `contextId -> sessionId` mapping, which the wrapper keeps in memory: core's `TaskStore`/`ResumeState` must persist that mapping (or `sessionStore`/`sessionId` option lets the provider choose the id deterministically from `contextId`, which would remove the need to store a mapping: `sessionId` must be a valid UUID, so derive a UUIDv5 from contextId [inferred]).
- A pending permission cannot be resumed across a restart unless the provider used the `PreToolUse` `defer` path from the start: the provider would return `defer`, end the query, record the deferred tool call in the core store, and later `resume` with the reply. The reply mechanism for a deferred call is [not found] in what I read: needs a spike. Without it core must fail the task ("pending interaction lost on restart") as the doc proposes.

**Auth**
- Map MCP `needs-auth` / URL-mode elicitation to `{kind:'auth', service, url}`; map account errors (`authentication_failed`, `billing_error`, `credits_required`) to `failed` with the SDK error code in `meta`. A `kind:'auth'` ask for Claude's own login is not natively possible in-band.

**Other model-shape notes for core types**
- `CoreInteractionResult` should be able to carry caller free text on `declined` (becomes the model-visible deny `message`), and `answered` for questions should carry a map keyed by question text.
- `CoreTaskState` may stay open for several Claude "turns" (results) per task; usage and cost reported per task should be derived from the last `result` (`total_cost_usd`, `modelUsage` cumulative) rather than summed.
- Input `CorePart[]` with images maps to content blocks only in streaming-input mode; text-only today in the wrapper.
- Capabilities by handler: Claude would implement `abortBackend`, `onMessage`, `resume`, the `ask` translation; `abortOrphan` can be omitted.
