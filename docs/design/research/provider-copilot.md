## Details per dimension

### D1 Run lifecycle and event stream

- Two ways to run a turn. `send()` posts RPC `session.send` and returns the `messageId` [verified: `node_modules/@github/copilot-sdk/dist/session.js:105-118`]. `sendAndWait(options, timeout)` subscribes to all events, calls `send`, and resolves when `session.idle` arrives; it rejects with `new Error(event.data.message)` on `session.error` and with `Timeout after Nms waiting for session.idle` after the timeout (default 60000) [verified: session.js:119-160]. The timeout "does not abort in-flight agent work" [verified: session.d.ts:114 doc comment]. Return value is the last `assistant.message` event or `undefined` [verified: session.d.ts:127].
- Event surface: `session.on(type, handler)` or `session.on(handler)` returns an unsubscribe function [verified: session.d.ts:150, 174]. Event list in 1.0.5 includes `session.start/resume/idle/error/shutdown/usage_info/plan_changed/todos_changed/task_complete`, `user.message`, `assistant.turn_start/turn_end/intent/reasoning/reasoning_delta/message_start/message_delta/message/usage/idle`, `tool.*`, `subagent.*`, `hook.*`, `permission.*`, `user_input.*`, `elicitation.*`, `sampling.*`, `mcp.oauth_*`, `external_tool.*`, `command.*`, `auto_mode_switch.*`, `exit_plan_mode.*`, `abort`, `model.call_failure`, `session.compaction_*` [verified: `grep` of `type: "..."` in `dist/generated/session-events.d.ts`].
- Streaming is opt-in: `SessionConfig.streaming: true` enables ephemeral `assistant.message_delta` / `assistant.reasoning_delta` [verified: types.d.ts ~1676 doc "Enable streaming of assistant message and reasoning chunks"]. Every event has `id`, `parentId`, `timestamp`, `ephemeral?`, `agentId?` (set for sub-agent events) [verified: session-events.d.ts:5339-5365 for PermissionRequestedEvent, same shape for all].
- Completion signal: `session.idle` (`IdleData.aborted?: boolean`; "no background agents or attached shell commands in flight") [verified: session-events.d.ts:868-885]. Final text is the last `assistant.message` (`data.content`).
- Errors: `session.error` data = `{errorType: string ("authentication","authorization","quota","rate_limit","context_limit","query", ...), errorCode?, message, statusCode?, stack?, url?, providerCallId?, eligibleForAutoSwitch?}` [verified: session-events.d.ts:797-840]. `model.call_failure` is a separate restricted-telemetry event. Rate-limit errors may be followed by an `auto_mode_switch.requested` event (an interaction, see D5) [verified: session-events.d.ts:804 comment]. Error types are plain strings, not a typed enum.
- Wrapper wiring: streaming path uses `send()` + `session.idle` + a `setTimeout` (default 600000 ms) that resolves with partial text; non-streaming uses `sendAndWait` raced against a timeout [verified: `a2a-copilot/src/copilot/executor.ts:388-662`]. Final text comes from accumulated `assistant.message_delta`, with `assistant.message` only as fallback [verified: executor.ts:394-421].
- Per-turn correlation: `assistant.turn_start/turn_end` carry `turnId`; `tool.execution_*` carry `turnId?`, `toolCallId`, `parentToolCallId?`; `user.message.interactionId?` [verified: session-events.d.ts:3413, 3829-3841, 2281-2292]. The wrapper does not filter by turn: its listeners are session-wide (see D8).

### D2 Abort / interrupt

- `session.abort()` -> RPC `session.abort`; doc: "Aborts the currently processing message in this session... The session remains valid and can continue to be used for new messages" [verified: session.d.ts:235-255; session.js:975-979]. Scope: the current turn of that session (not a specific message id, no `AbortSignal` parameter in 1.0.5). RPC type has `AbortRequest {reason?: AbortReason}` where reason is `user_initiated | remote_command | user_abort`, and `AbortResult {success, error?}` (the SDK `abort()` wrapper ignores the result) [verified: rpc.d.ts:1810-1830, 14736; session-events.d.ts:202-208].
- Observable effects: an `abort` event `{reason}` and `session.idle {aborted: true}` ("True when the preceding agentic loop was cancelled via abort signal") [verified: session-events.d.ts:3744, 868-885]. `sendAndWait` does NOT reject on abort; it resolves when idle arrives (with whatever `assistant.message` was last seen) [inferred from session.js:119-160, which rejects only on `session.error`].
- Races [inferred]: abort between `send()` resolving and the turn starting, queued messages (`enqueue`) are not necessarily cleared by abort; use `rpc.queue.clear()` too [verified that `queue.clear` exists: rpc.d.ts:15895]. Whether a pending permission prompt or `ask_user` call is cancelled by abort: not found.
- Wrapper: **does not call `session.abort()` at all**. `cancelTask` only logs, publishes `canceled`, and calls `bus.finished()`; the comment says "Copilot SDK doesn't expose a direct abort" which is wrong for 1.0.5 [verified: executor.ts:794-805]. The turn keeps running, keeps the session busy, and the still-pending `execute()` continues to publish into a finished bus.
- 1.0.34 unchanged: `abort(): Promise<void>` [verified: sdk34 session.d.ts:346]. Sub-agent / background-task abort is separate (`session.background_tasks_changed` event exists; not investigated further).

### D3 Steering (message while a turn is running)

- Native. `MessageOptions.mode?: "enqueue" | "immediate"`: "enqueue: Add to queue (default); immediate: Send immediately" [verified: types.d.ts:2174-2181]. The generated RPC text is more precise: "`enqueue` (default) appends to the message queue. `immediate` interjects during an in-progress turn" [verified: rpc.d.ts:1213-1223, marked `@experimental`].
- Observability of the outcome: `user.message.data.delivery` is `"idle"` (started its own run), `"steering"` ("Injected into the current in-flight run while the agent was busy (immediate mode)"), or `"queued"` ("Enqueued while the agent was busy; processed as its own run afterward") [verified: session-events.d.ts, `UserMessageDelivery`]. `pending_messages.modified` event fires when the queue changes (empty payload) [verified: session-events.d.ts:2794]. `session.rpc.queue.pendingItems()` returns `{items, steeringMessages: string[]}`, `queue.removeMostRecent()` and `queue.clear()` exist [verified: rpc.d.ts:9252-9266, 15879-15896; all `@experimental`].
- `SendRequest` additionally has `prepend?: boolean` (front of queue), `billable?`, `requiredTool?` [verified: rpc.d.ts:9903-9930]. The SDK's `MessageOptions` in 1.0.5 does not expose `prepend`; it is only on the raw RPC `session.rpc.send` [verified: types.d.ts:2139-2190 has no `prepend`].
- Not demonstrated: exactly where an immediate message is injected (next model call boundary vs. mid-tool) and what happens if `immediate` is sent while idle. `delivery:"idle"` for an idle session suggests it just starts a turn [inferred]. I did not run a live turn (cost).
- Wrapper: always calls `send({prompt})` with default `enqueue`; a second A2A message to the same context while a task runs would be queued as a new turn on the same session and its events would be mixed into the first task's listeners (see D8) [verified: executor.ts:570; inferred for mixing].
- 1.0.34 adds `MessageOptions.source?: "user" | "system" | agent-* | automation-*` [verified: sdk34 types.d.ts:3502-3518]; `mode` unchanged.

### D4 Agent-initiated permission requests

- Two delivery paths [verified: session.js:251-258, 372-400; client.js:997]:
  1. `onPermissionRequest(request, {sessionId})` handler registered at `createSession`/`resumeSession`. The SDK listens for the broadcast `permission.requested` event, calls the handler, and answers via RPC `permissions.handlePendingPermissionRequest({requestId, result})`. If the handler throws it answers `{kind: "user-not-available"}`. `{kind:"no-result"}` leaves the request unanswered. Events with `resolvedByHook: true` are skipped.
  2. No handler: session create sends `requestPermission: false`; per README "permission requests are emitted as events and left pending for the consumer to resolve with the pending permission RPC" [verified: README.md:852]. The consumer listens to `permission.requested` and calls `session.rpc.permissions.handlePendingPermissionRequest` **later and from any code path** (out-of-band answer is supported) [verified: rpc.d.ts:15585; "returns false when the request was already resolved"]. `permission.completed {requestId, result, toolCallId?}` tells UIs to dismiss [verified: session-events.d.ts:6018-6030].
- Request shape (`PermissionRequest`, discriminated on `kind`): `shell` (fullCommandText, commands[{identifier, readOnly}], intention, possiblePaths, possibleUrls, hasWriteFileRedirection, canOfferSessionApproval, warning?, requestSandboxBypass?), `write`, `read`, `mcp` (serverName, toolName, toolTitle, args, readOnly), `url`, `memory`, `custom-tool`, `hook`, `extension-management`, `extension-permission-access` [verified: session-events.d.ts:311, 5384-5700]. `PermissionRequestedData` also carries `promptRequest?: PermissionPromptRequest` (what the TUI would render: `commands`, `write`, `read`, `mcp`, `url`, `memory`, `custom-tool`, `path`, `hook`, ...) and `requestId` [verified: session-events.d.ts:5369-5382, 331, 5704-5733, 5901-5915]. Granularity is per tool call and, for shell, per parsed command identifier; the TUI offers "don't ask again for <command>" at repo/dir scope or for the session [verified: `copilot help permissions`].
- Decision options (`PermissionDecision`): `approve-once`, `approve-for-session` (optional `approval` of kind commands/read/write/mcp/mcp-sampling/memory/custom-tool/extension-*, optional `domain`), `approve-for-location` (persists to `~/.copilot/permissions-config.json`, needs `approval` + `locationKey`), `approve-permanently` (URL domain), `reject` (`feedback?` string shown to the model), `user-not-available` [verified: rpc.d.ts:6822-7200; README.md:905-913]. Result-side kinds (`approved`, `cancelled`, `denied-by-rules`, `denied-interactively-by-user`, `denied-no-approval-rule-and-could-not-request-from-user`, `denied-by-content-exclusion-policy`, `denied-by-permission-request-hook`) appear in `permission.completed` [verified: rpc.d.ts:997].
- Timeout / default when unanswered: **not found** in the SDK or its docs. The SDK adds no timer; a handler that never resolves leaves the tool call pending (the wrapper's own comment says it "hangs indefinitely in Docker / k8s / CI" without a handler [verified: session-manager.ts:229-232; a2a-copilot/CHANGELOG.md:113]). Non-interactive CLI mode "denies tool requests that no allow rule approves" [verified: `copilot --help` text for `--allow-all-tools`], but that is the CLI, not the SDK-hosted runtime.
- 1.0.34 adds `{kind: "attributed", result, decisionContext}` so the host can record "a human decided" (`permission.completed.decisionSource = "human_response"`), honoured only from the session's owning connection [verified: sdk34 types.d.ts:1176-1215]. Relevant for the core `by?: CoreCaller` field.
- Wrapper: `opts.onPermissionRequest = approveAll` everywhere (`approveAll = () => ({kind: "approve-once"})`) [verified: session-manager.ts:232; executor.ts:276; types.js:101]. In addition `McpEvidenceHooks.onPreToolUse` returns `{permissionDecision: "allow"}` for every call [verified: mcp-hooks.ts:104-105]. So the wrapper never surfaces a permission to the A2A caller; `input-required` is never emitted.
- Pre-tool hook alternative: `onPreToolUse` may return `permissionDecision: "allow" | "deny" | "ask"` with reason, `modifiedArgs`, `additionalContext` [verified: types.d.ts:867-875]. `"ask"` hands control to the normal permission flow [inferred]. A `permission.requested` with `kind:"hook"` and `PermissionDecisionDeniedByPermissionRequestHook` suggest a server-side permissionRequest hook concept [verified: session-events.d.ts:5635-5660, rpc.d.ts:7342]; not exposed as an SDK hook in 1.0.5.

### D5 Agent-initiated questions

- `ask_user`: enabled only if `onUserInputRequest` is provided [verified: types.d.ts:1621-1625; README.md:932]. Shape: request `{question: string, choices?: string[], allowFreeform?: boolean (default true)}`; response `{answer: string, wasFreeform: boolean}` [verified: types.d.ts:763-795]. Single question, single answer string; no multi-select, no JSON schema for ask_user. CLI flag `--no-ask-user` disables the tool [verified: `copilot --help`].
- Transport: server -> client JSON-RPC **request** `userInput.request` (the call blocks until the handler returns; if no handler it throws `User input requested but no handler registered`) [verified: client.js:1844-1846, 1920-1934; session.js:849-861]. In parallel the runtime emits ephemeral `user_input.requested {question, choices?, allowFreeform?, requestId, toolCallId?}` and `user_input.completed {answer?, requestId, wasFreeform?}` [verified: session-events.d.ts:6258-6355]. `session.rpc.ui.handlePendingUserInput` resolves a pending `user_input.requested` out-of-band; this is gated by `registerInterest` for event types such as `user_input.requested` so the runtime knows a consumer exists [verified: rpc.d.ts:15520, 9290].
- Elicitation (structured form): `onElicitationRequest(ctx) -> {action: "accept"|"decline"|"cancel", content?}`; ctx has `message`, `requestedSchema?` (`{type:"object", properties, required?}`), `mode: "form"|"url"`, `elicitationSource?` (MCP server name or absent for agent-initiated), `url?` [verified: types.d.ts:576-592, README.md:960-985]. Fan-out to all connected clients, first response wins [verified: README.md:991-994]. `session.ui.confirm/select/input/elicitation` let the host ask the user via the same machinery [verified: session.d.ts:83].
- Plan mode: `onExitPlanModeRequest({summary, planContent?, actions[], recommendedAction}) -> {approved, selectedAction?, feedback?}` [verified: types.d.ts:800-826]. Rate-limit mode switch: `onAutoModeSwitchRequest({errorCode?, retryAfterSeconds?}) -> "yes"|"yes_always"|"no"` [verified: types.d.ts:830-845]. MCP sampling: `sampling.requested` event [verified: event list]. All of these are additional agent->user interaction kinds that map to core `confirm`/`question`/`permission`.
- Wrapper: no `onUserInputRequest`, no `onElicitationRequest`, no plan-mode handler [verified: `grep onUserInput|onElicitation|onExitPlanMode` over `a2a-copilot/src` returned nothing]. Therefore `ask_user` is not even offered to the model.

### D6 Auth-required flows

- Startup auth: client option `gitHubToken` (takes priority), `useLoggedInUser` (stored OAuth/gh CLI), env tokens; `client.getAuthStatus()` returns `{isAuthenticated, authType?: "user"|"env"|"gh-cli"|"hmac"|"api-key"|"token", ...}` [verified: types.d.ts ~170-200 and 2295-2299; client.d.ts:238]. The SDK passes `--no-auto-login` when `useLoggedInUser` is false [verified: client.js:1589-1591].
- Runtime auth failure surfaces as `session.error` with `errorType: "authentication"` (or "authorization"/"quota"), carrying an optional `url` "the user can open in a browser" [verified: session-events.d.ts:797-840]. Not a pending interaction: the turn fails.
- MCP server OAuth: event `mcp.oauth_required {requestId, serverName, serverUrl, reason, wwwAuthenticateParams?, staticClientConfig?, resourceMetadata?}`; SDK handler `onMcpAuthRequest(request, {sessionId}) -> {accessToken, ...} | null` (null = cancelled); out-of-band via `session.rpc.mcp.oauth.handlePendingRequest` [verified: session-events.d.ts:6576-6666; types.d.ts:1284-1344; session.js:259-272, 399-410]. If no handler is registered the SDK only `console.warn`s and the request stays pending [verified: session.js:259-268]. With no registered interest the runtime "silently reuses cached tokens" (browserless fallback) [verified: rpc.d.ts:9290 doc text].
- 1.0.34: `ProviderTokenArgs` / bearer-token provider callbacks (managed identity for BYOK) are `@experimental` [verified: sdk34 types.d.ts ~3205].
- Wrapper: maps start failures containing "auth/login/token/unauthorized" to a text error [verified: executor.ts:172-191] and (mis)maps any runtime error containing "permission" to "GITHUB_TOKEN not set" [verified: executor.ts:737-741]. No `auth-required` state ever emitted.

### D7 Persistence / resume across restarts

- Persistent state is on disk (`~/.copilot` or `baseDirectory`/`COPILOT_HOME`): "Session state on disk (conversation history, planning state, artifacts) is preserved [after disconnect()]" [verified: session.d.ts:211-231; types.d.ts CopilotClientOptions.baseDirectory]. `client.resumeSession(sessionId, ResumeSessionConfig)`, `listSessions(filter?)`, `getSessionMetadata`, `getLastSessionId`, `deleteSession` exist [verified: client.d.ts:187-325]. `createSession({sessionId})` lets the caller choose the id (so core's `contextId` can be the Copilot session id) [verified: types.d.ts:1850; README.md:719-727]. Infinite sessions (default) persist to `workspacePath` with background compaction [verified: README.md:651; session.d.ts:61-65].
- Handlers are not persisted: `resumeSession` needs `onPermissionRequest`, `onUserInputRequest`, tools, hooks etc. passed again [verified: client.js:1092-1130].
- Pending interactions across restart: `ResumeSessionConfig.continuePendingWork?: boolean` (default false): "the runtime continues any tool calls or permission prompts that were still pending when the session was last suspended... For permission requests, the runtime re-emits `permission.requested` so the registered `onPermissionRequest` handler can re-prompt; for external tool calls, the consumer is expected to supply the result via the low-level RPC" [verified: types.d.ts:1862-1880]. `session.rpc.permissions.pendingRequests()` "reconstructs the set of pending tool permission requests from the session's event history" (permission.requested without matching permission.completed) [verified: rpc.d.ts:15591, 6809]. So **permissions can survive a restart (native, with `continuePendingWork`)**.
- `user_input.requested` and `elicitation.requested` are `ephemeral: true` (not persisted), and `userInput.request` is a live JSON-RPC call tied to the dead connection, so a pending question does **not** survive [verified: session-events.d.ts:6258-6285 ephemeral flag; inferred for the call semantics]. A question pending at restart is lost; core would have to re-ask via the model (or fail the task).
- 1.0.34 adds `TranscriptRecovery` (repair of corrupted transcripts on resume, `allowTranscriptRecovery`) [verified: sdk34 types.d.ts:3172, 3205-3213].
- Wrapper: in-memory `Map<contextId, SessionEntry>`, TTL 1 h, `disconnect()` on expiry/shutdown, never calls `resumeSession` or `listSessions` [verified: session-manager.ts:67-71, 207-224, 296-326]. After a process restart every context gets a fresh Copilot session and loses history (although the old one still exists on disk).

### D8 Concurrency

- One `CopilotClient` = one runtime process (stdio) hosting many independent `CopilotSession`s [verified: README.md:706-716 "Multiple Sessions ... independent"; client.js `this.sessions` map]. Sessions are keyed by `sessionId`; handlers are per session.
- Within one session: sends are queued FIFO (`enqueue`), or injected (`immediate`) [verified: see D3]. So "multiple turns per session" is supported as a queue; not parallel.
- Wrapper hazards [verified from code, consequence inferred]: (a) event listeners are attached to the shared session per `execute()` and filter nothing by turn/task, so two tasks in one contextId would both receive each other's deltas and the first `session.idle` completes the first task; (b) `McpEvidenceHooks` is one instance with one `emitter` for the whole client: `setEmitter` at execute start and `clearEmitter` at the end of any task clobber concurrent tasks (executor.ts:345-347, 757-758; mcp-hooks.ts:56-64); (c) `sessionManager.taskSessions` supports many tasks but `cancelTask` does nothing with it.
- Session-level server option `sessionIdleTimeoutSeconds` (spawned runtime only) auto-cleans idle sessions [verified: types.d.ts:280; client.js:1592-1598]. No documented cap on concurrent sessions: not found.

## Gaps and surprises

1. **Wrapper leaves nearly all interaction/control features unused**: no abort, no `onUserInputRequest` (so `ask_user` is never offered), no elicitation, no plan-mode or auto-mode-switch handler, no `resumeSession`, no `mode:"immediate"`, no attachments. `approveAll` plus an always-`allow` `onPreToolUse` means permissions are never shown to the caller.
2. **`cancelTask` is a no-op toward Copilot** and its comment ("SDK doesn't expose a direct abort") is wrong for 1.0.5; `session.abort()` exists since at least 1.0.0 [verified: executor.ts:796; session.d.ts:255].
3. **Steering is native but experimental and under-specified**: `mode:"immediate"` exists, and its result is observable only after the fact through `user.message.delivery` (`steering` vs `queued`); `send()` itself returns only a `messageId`. Core's `MessageOutcome` (`accepted | queued | rejected`) can be derived by reading `delivery` from the `user.message` event whose id matches [inferred]. I did not run a live test.
4. **Permissions have an out-of-band answer path** (no handler -> pending event -> RPC later), with a durable log (`pendingRequests`, `continuePendingWork`); that is exactly what core's persisted-interaction model needs. Questions (`ask_user`, elicitation) do not have the durable half: ephemeral events plus a blocking JSON-RPC request.
5. **No timeout anywhere**: no default decision on unanswered permission or question [not found]; `sendAndWait` has a 60 s default that does not abort work.
6. **Session-wide event stream with no per-task isolation**: concurrent or queued tasks in a single session mix events; `turnId`/`interactionId`/`toolCallId` exist but the wrapper does not use them.
7. **Version drift**: installed SDK 1.0.5 vs latest 1.0.34, bundled runtime 1.0.68 vs machine CLI 1.0.114; 1.0.34 changes packaging (platform optional deps, in-process transport) and adds `permissionMode`, `AttributedPermissionResult`, typed structured output, `TranscriptRecovery`.
8. **Error taxonomy is stringly typed** (`errorType`, `errorCode` strings), and the wrapper's error classification relies on message substrings (executor.ts:735-741), mislabelling "permission" errors as missing GITHUB_TOKEN.
9. `session.send` after `disconnect()` throws; a session expired by the wrapper's TTL loses its in-memory handler set, but on-disk state remains (resume possible but not implemented).
10. Several kinds of agent->user requests beyond permission/question exist (exit plan mode, auto-mode switch after rate limit, MCP sampling, MCP OAuth, session-limits-exhausted). A closed `CoreInteraction` union with only `permission|question|auth|confirm` can host them, but `plan-review` and `rate-limit-switch` would map to `confirm`/`question` with `detail` metadata.

## Implications for a provider-neutral contract

What a Copilot provider would have to do for each handler (all provider-local, none needs core to know it is Copilot):

- **`run(request, run)`**: get-or-create a `CopilotSession` keyed by `contextId` (pass `sessionId: contextId` on create to make resume trivial), register `onPermissionRequest`, `onUserInputRequest`, optionally `onElicitationRequest`, `onExitPlanModeRequest`, `onAutoModeSwitchRequest`, `onMcpAuthRequest`. Send with `session.send({prompt, attachments})` and treat `session.idle` (not `sendAndWait`'s 60 s) as completion. Convert CorePart `file`/`bytes` to `attachments` (`file` path or `blob`). Filter events by `turnId`/`interactionId` (or by the `messageId` returned from `send`) so core's per-task inbox works; stop using a singleton `McpEvidenceHooks` emitter.
- **Permission -> `run.ask({kind:"permission"})`**: map `PermissionRequest.kind` (`shell|write|read|mcp|url|memory|custom-tool|hook`) to `action` (kind), `target` (command text / path / URL / `serverName.toolName`), `risk` (`readOnly`, `warning`, `requestSandboxBypass`, `possibleUrls`), `detail` (raw request, `toolCallId`). Offer options derived from the request: `approve-once`, `approve-for-session` only if `canOfferSessionApproval` (shell) or the request is not path/url, `reject` (+ feedback). Map `CoreInteractionResult` back to `{kind:"approve-once"|"approve-for-session"|"reject",feedback}`; map `timeout`/`canceled` to `{kind:"reject"}` or `user-not-available` (the SDK has no default, so the provider must always answer, otherwise the tool call hangs). `approve-for-location` and `approve-permanently` persist outside the session; core should not offer them by default.
- **Question -> `run.ask({kind:"question"})`**: `choices` -> `Choice[]`, `allowFreeform` -> whether free text is accepted, return `{answer, wasFreeform}`. Elicitation `requestedSchema` -> `schema` and `{action, content}` back; `mode:"url"` -> `kind:"auth"` or `question` with `url`. `ask_user` carries one string only; core's `multi`/`schema` richer shapes would not be producible by this provider except through elicitation.
- **`onMessage` (steer)**: implement with `session.send({prompt, mode:"immediate"})`; then wait for the `user.message` event whose `delivery` is `steering` -> `accepted`, `queued` -> `queued`, `idle` -> treat as `queued`/new turn. Needs a small provider-local correlation (message id from `send` vs `user.message.id`). Because `immediate` is under `@experimental` RPC types, the provider should catch errors and fall back to the workaround "abort + resend merged prompt" (`session.abort()` then `send` once `session.idle {aborted:true}` arrives) for steering failures. If `onMessage` is absent, `enqueue` is a natural default, which is also what Copilot would do itself.
- **`abortBackend`**: `session.abort()`, then await `session.idle` (`aborted:true`) or the `abort` event; also `rpc.queue.clear()` to drop queued follow-ups, and answer or drop any pending permission/question (`handlePendingPermissionRequest({kind:"reject"})`) so the turn can unwind. Session remains reusable. Provide a bound (timeout) since `abort()` just acknowledges the request and the turn can end later [inferred].
- **`abortOrphan`**: for a durable store with no live run: `client.resumeSession(contextId, {onPermissionRequest})` then `abort()` + `disconnect()`, or `client.deleteSession(contextId)` to discard; both exist.
- **`resume(state)`**: `resumeSession(contextId, {continuePendingWork:true, onPermissionRequest, ...})`; Copilot re-emits `permission.requested` so the provider can call `run.ask` again from the persisted interaction (core's `resume` handler = "rebind pending interaction to the re-emitted request id"). Alternative with no handler: use `permissions.pendingRequests()` and answer later with `handlePendingPermissionRequest`. Pending **questions cannot be resumed**: the provider must report that to core (e.g. fail with a precise reason, or re-ask the model), so `resume` must be allowed to return "cannot restore interaction X".
- **Interaction ids**: Copilot already has stable `requestId` for permission/user-input/elicitation/oauth and `toolCallId`; core's persisted interaction record should keep a provider-opaque `correlation` field (the `requestId`) to bind a resumed run.
- **Auth**: Copilot has no pending "login required" interaction. A provider should translate `session.error` with `errorType: "authentication"` (and `url`) to `run.fail` or to `run.ask({kind:"auth", service:"github-copilot", url})` followed by a retry; MCP OAuth (`mcp.oauth_required`) maps cleanly to `kind:"auth"` (`service: serverName`, `url: serverUrl`, answer = token or cancel, via `onMcpAuthRequest`).
- **Core-side policy that Copilot makes easy to delegate**: auto-approve rules can be applied in core (before `ask` is surfaced) or provider-side with `permissions.modifyRules`/`permissionMode` (1.0.34). Core should keep the policy in core (`risk`/`action`) and the provider just returns the decision, to avoid two sources of truth.
- **Open design hints for the domain model**: (1) `CoreInteractionResult` needs `feedback?` (text to the model on reject) and an optional `scope` (`once|session|location`) because Copilot has all three; (2) `CorePart` needs `blob/mimeType` (already covered by `file`) and tool results with images; (3) `TaskRun` needs a way for the provider to say "interaction was resolved elsewhere" (Copilot broadcasts `permission.completed`, first answer wins, `handlePending*` returns false if already resolved); (4) `status` events benefit from a typed `progress` kind (`tool`, `plan`, `todos`, `reasoning`, `subagent`) rather than free text; (5) usage events (`inputTokens`, `cost`, `tokenLimit`) are rich enough to define a core `usage` event; (6) interaction `timeout` default must live in core because Copilot has none.
