Research date: 2026-11-21. Read-only investigation. Evidence labels: [verified: source] or [inferred].

## Details per dimension

### D1 Run lifecycle and event stream

v1 (wrapper's `client.ts`): `sessionPromptAsync` -> `POST /session/{id}/prompt_async` returns "Prompt accepted"; the turn runs on the server; the wrapper watches an SSE stream and treats `session.idle` as completion and `session.error` as failure, with a polling fallback (`sessionIdle` via `session.status`) [verified: S1 executor.ts:315-350, 591-620; S2 SessionPromptAsyncData]. A blocking `POST /session/{id}/message` (`SessionPromptData`) also exists [verified: S2 types.gen.d.ts:8357]. `SessionStatus` = `idle | busy | retry{attempt,message,next,action?}` [verified: S2 types.gen.d.ts:504; S3 types.d.ts:447].

v2: prompt is "durably admitted" to the session's inbox and execution is scheduled "unless resume is false" [verified: S6; S3 SessionPromptInput.resume]. Event types observed in `@opencode/client` 2.3.2 include `session.execution.started/succeeded/failed/interrupted`, `session.idle`, `session.status`, `session.step.started/streamed/ended/failed`, `session.text.started/delta/ended`, `session.reasoning.*`, `session.tool.input.started/delta/ended`, `session.tool.called/progress/success/failed`, `session.retry.scheduled`, `session.inbox.enqueued/delivered/cancelled/delivery.changed`, `permission.asked/replied`, `form.created/replied/cancelled` [verified: S3 types.d.ts grep of `type: "..."`]. `GET /api/event` is "Volatile by contract: a slow consumer overflows and fails the stream, and events during disconnection are missed"; durable replay is via `GET /api/experimental/session/{sessionID}/log` (`follow=true` for live) [verified: S6]. The wrapper's v2 client translates these into the 1.x shapes inside `translateEvent` [verified: S1 client-v2.ts:translateEvent]. Note the wrapper subscribes to the global stream and filters by `sessionID` client-side [verified: S1 event-stream.ts].

### D2 Abort / interrupt

v1 `POST /session/{sessionID}/abort` returns boolean; assistant message gets a `MessageAbortedError` [verified: S2 SessionAbortData, AssistantMessage.error union]. v2 `POST /api/session/{sessionID}/interrupt?resume=` returns `{interrupted: boolean}`; "interrupts execution owned by this process", an idle session is a no-op; `resume=true` runs pending steer items and next-in-line control items while queued prompts stay parked [verified: S6; S3 SessionInterruptInput]. Event `session.execution.interrupted` has `reason: "user" | "shutdown" | "superseded" | "inactivity"` [verified: S3 types.d.ts:1884]. Scope: the whole session execution (cannot target a single tool/turn). What stays valid: the session and its history, inbox items (unless cancelled). Important: "owned by this process" means in a multi-server setup an interrupt only works against the process that owns the run [verified: S6]. Wrapper `cancelTask` calls `sessionAbort` then publishes `canceled`; it ignores abort failures [verified: S1 executor.ts:730-745].

### D3 Steering

v2 has a first-class steering model [verified: S3]:
- `SessionPromptInput.delivery?: "steer" | "queue"`; `SessionInboxDelivery = "steer" | "queue"` (types.d.ts:124, 4379).
- `session.inbox.update {sessionID, inboxID, delivery}` changes an item's mode; `session.inbox.cancel` cancels an undelivered item; `session.inbox.list` lists pending; events `session.inbox.enqueued/delivered/cancelled/delivery.changed`.
- Client store logic computes a pending item status as `queued` (delivery queue), `starting` (idle session, will start), `steering` (active run, delivered at boundary) or `stranded` (idle session whose item predates the last idle marker) [verified: chunks/service-timing-mqnb71k6.js:1340-1349].
- Semantics from docs: steering runs "at the next step boundary instead of waiting behind queued prompts"; "Steering wakes session execution" [verified: S6]. Client-side default when `delivery` is omitted is `"steer"` (`request.delivery ?? "steer"`, line 1488); the server-side default for a raw HTTP call is not stated [inferred: same].
- Consequence for the current wrapper: `client-v2.ts` `session.prompt` call omits `delivery` [verified: S1 client-v2.ts sessionPromptAsync], so a second A2A message on a busy context steers the running turn on 2.x, whereas on 1.x it follows 1.x's busy-session behavior. Neither is controlled by the wrapper.
v1: no mode flag in `SessionPromptAsyncData` (fields: messageID, model, agent, noReply, tools, format, system, variant, parts) [verified: S2 types.gen.d.ts:8659-8675]. Behavior for a prompt posted to a busy v1 session: the running loop picks up the new user message at its next step (injection) [inferred from OpenCode's loop design; not verified in the sources read]. So v1 gives steer-like behavior with no ability to choose queue; if "queue as next turn" is required, the provider must hold the message itself until `session.idle` (provider-local workaround).

### D4 Permission requests

Shape (v1): `PermissionRequest{id, sessionID, permission, patterns[], metadata, always[], tool?{messageID, callID}}`; `permission` is the tool/action name (`read`, `edit`, `bash`, `external_directory`, ...); `always` lists the patterns that would be saved if "always" is chosen [verified: S2 types.gen.d.ts:2028-2040, 5883]. Shape (v2): `{id, sessionID, action, resources[], save?[], metadata?, source?{type:"tool", messageID, id}, message?}` [verified: S3 types.d.ts:1137, 2602].
Replies: `once | always | reject` plus optional `message` (feedback to the model) [verified: S2 PermissionReplyData; S3 PermissionReplyInput]. Semantics: `once` approves just this request; `always` approves and saves the proposed patterns as project-scoped allow rules (never overriding a configured deny); `reject` rejects this request AND every other pending permission request in that session [verified: S7].
Asynchrony: the request is a held state on the server; list endpoints (`GET /permission`, `permission.request.list`, `permission.list` per session) make it recoverable by polling, so an out-of-band late reply is possible while the server process and session live [verified: S2/S3 list endpoints; S1 permission-handler.ts `handlePending`]. v2 replies are session-scoped: the caller must know `sessionID` for the `requestID` (wrapper keeps a map and falls back to listing) [verified: S1 client-v2.ts:permissionReply].
Timeout/default if unanswered: not documented ("The page doesn't document a timeout") [verified: S7]; the tool call stays blocked [inferred]. Reload of a location cancels pending permissions and forms [verified: S6].
Current wrapper behavior: auto-answers everything: `autoApproveAll` default true replies `always` (the saved-rule variant!), otherwise `reject`; also pre-seeds a session ruleset of allow rules so most requests never fire [verified: S1 permission-handler.ts:44-50,86-99; session-manager.ts AUTO_ALLOW_PERMISSIONS]. Because the default reply is `always`, the headless wrapper writes persistent project rules as a side effect [verified: S1 permission-handler.ts default `defaultPermissionReply: "always"` + S7 semantics].

### D5 Questions / user input

v1: the `question` tool emits `question.asked{id, sessionID, questions: QuestionInfo[], tool?}`; `QuestionInfo{question, header (<=30 chars), options:[{label, description}], multiple?, custom?}`; `custom` allows free-text answers; reply `POST /question/{requestID}/reply {answers: string[][]}` (one array of selected labels per question) or reject; events `question.replied`, `question.rejected` [verified: S2 types.gen.d.ts:532-552,5964, QuestionReplyData]. Permission to use the tool is itself an action `question` (allowed for `build` and `plan`, denied for `general`) [verified: S7].
v2: questions are generic "forms": `FormInfo{id, sessionID, title, metadata?, fields: [FormField,...]}`; field types `string` (format email/uri/date/date-time, min/max length, pattern), `number`, `integer`, `boolean`, `multiselect` (options{value,label,description}, minItems, maxItems, custom, default), `external` (url); fields have `required`, `hidden`, `when` conditions; answer `{[key]: string|number|boolean|string[]}`; cancel optionally with a message [verified: S3 types.d.ts:172-193,928-943,1561; S6]. Forms can be created by clients too (`session.form.create`), not only agents. The wrapper maps forms to `QuestionRequest` and builds answers from `string[][]` [verified: S1 client-v2.ts:buildFormAnswer, toQuestionRequest]. How the `question` tool maps to a form is not described in the docs read [verified: S6 summary]. The wrapper's default is to auto-answer with the first option of each question (or `""`) [verified: S1 permission-handler.ts:122-127].

### D6 Auth-required flows

- Provider (LLM) auth: v1 `AssistantMessage.error` includes `ProviderAuthError`; `SessionStatus.retry.action{reason, provider, title, message, label, link?}` is a structured "you need to do X" payload with a link [verified: S2 types.gen.d.ts:221, 504-520; S3 types.d.ts:447-462]. v2: integrations API (`integration.connect.key/external`, `integration.oauth.connect/status/complete/cancel`, `integration.command.connect/status/cancel`), credentials API; events `integration.updated`, `credential.updated`, `credential.switched` [verified: S3 client.d.ts, types.d.ts event list]. CLI `opencode auth` / `opencode acp --login` [verified: S4].
- MCP auth: `McpStatus` variants `connected | pending | disabled | failed | needs_auth | needs_client_registration` [verified: S3 types.d.ts:365-380; S1 types.ts MCP exports].
- Server auth: v2 requires HTTP Basic (username `opencode`, random password printed at startup); the wrapper throws `OpenCodeAuthError` on 401/403 and exits at startup; also pairing codes (`POST /api/pair`, `GET /auth/connect/{code}`) [verified: S1 README.md:142-162, backend.ts; S6].
No event says "agent is blocked waiting for provider login"; auth failures arrive as `session.error` / `session.step.failed` or retry-status with an action link [inferred from the above types].

### D7 Session persistence and resume

Sessions live in the OpenCode server (sqlite-backed durable event log in v2, with `durable{aggregateID, seq}` on `session.*` events; `session.list` with cursors; fork, revert, export/import) [verified: S3 types.d.ts, client.d.ts (`session.fork`, `revert.*`, `experimental.session.import/export`)]. After an A2A wrapper restart the server still holds sessions, but a2a-opencode keeps `contextId -> sessionId` in memory (TTL map), so context is orphaned; persisting the mapping (or deriving a session title/metadata `contextId`) would make resume trivial [verified: S1 session-manager.ts]. CLI also supports `--session <id>`/`--continue` [verified: S4 `run --help`].
Pending permission/question after restart:
- Wrapper restart, server alive: the permission/question is still pending on the server and listable (`permissionList`, `questionList`/`form.list`), so a new wrapper process could find and answer it (provider-local `resume`) [verified: list endpoints; inferred about restart].
- Server restart: pending asks are not on the durable event stream (no `durable` field on `permission.asked`/`form.created`) and a location reload cancels them [verified: S3 types.d.ts; S6]. The interrupted run would be marked `session.execution.interrupted{reason:"shutdown"}` [verified: S3 types.d.ts:1884].

### D8 Concurrency

Server hosts many sessions; one running agent loop per session. v2 inbox serializes work per session; `queue` items wait, `steer` items are folded in at step boundaries [verified: S3; S6]. `GET /api/session/active` lists "foreground drains owned by this process" [verified: S6]. Prompt can return 409 Conflict [verified: S6 summary]. v1: `session.status` map and `session.idle`. Wrapper: one `EventStreamManager` (SSE connection) per execution, filtered by session id client-side, so N concurrent tasks mean N SSE subscriptions to the global event stream [verified: S1 executor.ts:470; event-stream.ts]. Subagents: `task` tool creates child sessions with `parentID` (session create accepts `parentID`) [verified: S1 client-v2.ts sessionCreate; S2 sdk types].

### D9 Tool, MCP, reasoning, plan, todo events

v1 `Part` union: `TextPart | SubtaskPart | ReasoningPart | FilePart | ToolPart | StepStartPart | StepFinishPart | SnapshotPart | PatchPart | AgentPart | RetryPart | CompactionPart` [verified: S2 types.gen.d.ts:474]. `ToolPart.state` = pending | running | completed | error with input/output/time [verified: S1 types.ts exports]. Todos: event `todo.updated`, `Todo` type [verified: S1 types.ts]. v2 granular events listed in D1; tool progress `session.tool.progress`; plus MCP code-mode: on 2.x MCP tools are invoked through an `execute` tool, so tool names are not MCP tool names [verified: S1 README.md:168]. MCP management APIs: `mcp.list`, `experimental.mcp.add/connect/disconnect/remove`, `mcp.status.changed`, `mcp.resources.changed` [verified: S3 client.d.ts; S1 client-v2.ts].

### D10 Input modalities and outputs

v1 input parts: `TextPartInput`, `FilePartInput{mime, url, filename}` (data: or file: URLs), `AgentPartInput`, `SubtaskPartInput`; `format` = `text | json_schema{schema, retryCount}` yielding `AssistantMessage.structured`; `StructuredOutputError` exists [verified: S2 types.gen.d.ts:116-127,243,8659-8675]. v2 input: `text`, `files[{uri, source: inline|uri, name, description, mention}]`, `agents[]`, `skills[]`, `metadata`, `delivery`, `resume`; no `format`/output-schema field in `SessionPromptInput` (not found) [verified: S3 types.d.ts:4340-4381]. Wrapper drops `subtask` parts on 2.x (sent as text) [verified: S1 client-v2.ts, README.md:170]. Output of file changes: v1 `PatchPart`, `SnapshotFileDiff{file,patch,additions,deletions,status}` and `session.diff` event; v2 `session.diff`/`FileDiffInfo`, `vcs.diff` [verified: S2, S3]. Images returned by tools: v2 `media` endpoints (`experimental.media.get`) [verified: S3 client.d.ts]. A2A file parts are not currently mapped by the wrapper [inferred from `buildPromptBody` in README/executor, not read in detail].

### D11 Usage, cost, context

v1: every completed assistant message carries `cost` and `tokens{total?, input, output, reasoning, cache{read,write}}` plus `modelID/providerID`; the wrapper derives a `UsageCallRecord` per assistant message [verified: S2 types.gen.d.ts:213-246; S1 executor.ts:`usageRecordFromMessage`]. v2: `session.step.ended` (cost, tokens) is translated by the wrapper into the same shape; `session.usage.updated{cost,tokens}` (running total), `session.usage.recorded{source: title|compaction|generate}` for side calls; `GET /api/experimental/session/stats` [verified: S1 client-v2.ts:translateEvent; S3 types.d.ts:2384-2503; S6]. Context-window size or utilization events: not found. Cost is provided by the server (USD) which is rarer than Codex.

### D12 Approval policy configuration

Rules: `PermissionRule{permission, pattern, action: allow|deny|ask}` (v1) and `{action, resource, effect}` (v2); order matters, last match wins; wildcard `*`/`?`; if several resources are checked any `deny` denies, else any `ask` prompts; default fallback `ask`, but each agent's base policy begins with an allow-all rule [verified: S2 types.gen.d.ts:57-63; S7]. Built-in actions: `read, edit, glob, grep, shell, subagent, skill, question, webfetch, websearch, external_directory` [verified: S7]. Scope levels: global/project config, agent definition, per-session `permission`/`permissions` set at `session.create`, `session.permissions` event (durable), project-saved approvals (`permission.saved.list/update/remove`), `policies` that can only deny and override project config [verified: S3 client.d.ts, types.d.ts:3315; S7]. There is no sandbox like Codex's; isolation is permissions + `external_directory`. CLI `--auto` = "Auto-approve permissions that are not explicitly denied" [verified: S4]. The wrapper's version difference: shell action is `bash` (1.x) vs `shell` (2.x); it emits both [verified: S1 client-v2.ts:toV2Permissions].

### D13 Hooks

Plugin system exists (`opencode plugin`, events `plugin.updated`, `plugin.added`, RPC events over `/api/event`) [verified: S4, S3, S2 event list]. A per-tool pre/post hook API for external clients: not found in the sources I read. The server-side event stream plus the permission ask/reply protocol cover what a wrapper needs; `session.synthetic` (v2) lets a client inject a synthetic message (`SessionInboxSynthetic`) [verified: S3 client.d.ts `session.synthetic`].

## Gaps and surprises

1. Strong positive surprise: 2.x has a real steering model (`delivery: steer|queue`, inbox list/update/cancel). It is the only provider of the two researched with a native queue-vs-inject switch. The wrapper does not use it (omits `delivery`).
2. Current wrapper auto-replies `always` to permissions by default, persisting project-level allow rules as a side effect of headless runs; core's `run.ask` auto-answer policy should default to `once`.
3. `reject` aborts every pending permission request in the session, not just one; an interaction model with independent per-request denial cannot be assumed [verified: S7].
4. Permission replies in v2 are session-scoped (need `sessionID`); `GET`-by-id for v1 is not needed but listing is directory-scoped.
5. Questions differ structurally between generations (v1 option lists with `multiple`/`custom`; v2 typed forms with validation and conditions). The wrapper's `string[][]` canonical shape is lossy for numbers/booleans/conditional fields [verified: S1 client-v2.ts:buildFormAnswer coerces by field type].
6. No documented timeout for permissions/questions: if the caller never answers, the run hangs on the server; core must own the timeout and issue the reply (`reject`/`cancel`) itself.
7. `/api/event` is volatile (missed events on disconnect); reconnection logic needs to reconcile via `permission.list`, `form.list`, `session.active` and the durable log. The wrapper polls `handlePending` as a safety net [verified: S1 executor.ts:337,758].
8. Interrupt is "owned by this process": multi-instance/cluster cancel needs routing to the owning server.
9. Sessions persist but the wrapper's context map does not; resume after wrapper restart is a missing feature, not an OpenCode limitation.
10. Output schema (structured output) exists in v1 but was not found in v2's prompt input.
11. Version skew: `@opencode-ai/sdk` 1.17.14 installed vs 1.19.6 latest; `@opencode/client` pinned exact 2.3.2 which is `latest`.
12. Not found: V1 docs content, v1 behavior for prompts to a busy session (inferred), v2 server default for `delivery`.

## Implications for a provider-neutral contract

- Permission bridge: OpenCode `permission.asked` -> `CoreInteraction{kind:"permission", action: permission|action, target: patterns|resources (array), options}`. Options needed: `once`, `always` (with the list of patterns that would be saved: `always`/`save`, so core can show what "always" persists), `reject`. `PermissionOption` therefore needs a `persists: string[]` detail and a free-form `feedback` message (OpenCode accepts `message` on reject and on reply). Also needs the flag "rejecting cancels sibling requests", or core must reply sequentially knowing siblings die.
- Out-of-band answer: a provider `resume`-style hook is realistic for OpenCode: on core restart, call `permissionList`/`form.list` to re-attach pending interactions to the durable core store. So `resume?(state)` for OpenCode = re-list pending asks for the stored session id and re-emit `ask`; core should persist `{providerSessionId, providerRequestId, kind, sessionScope}` per pending interaction.
- Timeouts: core must own them and produce `outcome: "timeout"`, which the provider translates to `reject` (permission) or form cancel / question reject. Do not rely on OpenCode for timeouts.
- Auto-answer policy: core's operator rules (auto-approve low risk) replace the wrapper's `autoApprovePermissions`; default `once`, never silently `always`.
- Questions: `CoreInteraction{kind:"question"}` should accept a list of sub-questions, each with `choices`, `multi`, `allowCustom` (v1 `custom`), and optionally typed fields (a JSON-schema `schema` covers v2 forms: string formats, number, integer, boolean, multiselect, conditional `when`). The provider converts core's answer map back to `string[][]` (v1) or `{[key]: value}` (v2). `CoreInteractionResult.value` should therefore be a keyed map, not a single string.
- Steering: `onMessage(run, message)` for OpenCode 2.x = `session.prompt {delivery:"steer"}` (outcome `accepted`) or `{delivery:"queue"}` (outcome `queued`); core's "queue as next turn" default maps to `delivery:"queue"`, and `inbox.update/cancel` give the provider the means to revoke a queued message when the task is cancelled. Return the inbox item id so core can track it (`session.inbox.delivered` event completes the story). For OpenCode 1.x the provider would post the prompt (injection at the next step, inferred) and report `accepted` only (no `queued`); if core's contract demands `queued`, the 1.x provider must hold the message locally until `session.idle`. Since both live in one wrapper today, the provider should implement `onMessage` per generation behind its existing `OpenCodeBackend` interface.
- Abort: `abortBackend(runInfo)` = `session.abort` (v1) / `session.interrupt {resume:false}` (v2); runInfo needs the provider session id. `abortOrphan` for OpenCode is real and cheap (session survives, so a stale run after wrapper restart can be interrupted by session id, `session.active` tells whether anything is running); core should be able to call it with `{taskId, contextId}` and the provider resolves the session from its stored mapping. After abort, the session remains valid for the next turn. Consider `interrupt {resume:true}` as an opt-in for "abort but run what the caller queued".
- Resume: persist `contextId -> sessionId` (and generation kind, directory) in the core store as `ResumeState`; `session.get` verifies it still exists.
- Events/usage: neutral vocabulary should include per-step usage with cost and token breakdown including cache read/write (OpenCode supplies cost), tool-call lifecycle with progress, reasoning, todo list, diffs/patches (path, patch text, additions/deletions), retry (`attempt`, `message`, `next`, optional `action` with a link) mapping to a status text or `auth-required` when `action.link` is present.
- Auth: `CoreInteraction{kind:"auth", service: provider, url: action.link, instructions: message}`, derived from `session.status.retry.action` or MCP `needs_auth`; completion is out-of-band (the user authenticates in OpenCode; the retry then succeeds), so core needs a way for the provider to resolve an auth interaction without a caller message (a `run.ask` that resolves on provider signal) or let the caller reply "done" and retry.
- Neutral flags avoided: capability = presence of `onMessage`, `resume`, `abortOrphan`; here all three are implementable on both generations (with the v1 `queued` caveat).
- Version/generation detection and the 1.x/2.x translation layer must stay inside the provider; core types should not mirror either generation's names.
