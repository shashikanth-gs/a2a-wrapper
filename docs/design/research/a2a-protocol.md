## 2. Summary table

| Topic | Spec says | SDK 1.0.0 (installed) does | Gap / ambiguity |
|---|---|---|---|
| Streaming close at `input-required` | Stream MUST close on terminal state (§3.1.2, §3.1.6). §11.7 prose says close at "terminal or interrupted". Interrupted vs stream-close not otherwise stated. 1.1 (`dev-1.1`, PR #2270 merged 2026-10-13): non-terminal state SHOULD NOT close stream | Closes stream/blocking call at `input-required` (queue stop set); does NOT close at `auth-required` | Spec internally inconsistent in 1.0.1; SDK matches §11.7 for input-required, not §3.1.2. Clients must handle both |
| Message to a `WORKING` task | "Agents MAY accept additional messages for tasks in non-terminal states" (§3.3.3). No rule on semantics | Starts a **second concurrent `execute()`** on the same task and same bus; no guard | Undefined in spec; unsafe in SDK. Fix (a2a-js PR #632) is still open |
| Message to `input-required` task | Client replies with new message, same `taskId` (+`contextId`) (§3.4.3, §6.3) | Loads task, appends message to history, runs `execute()` again with `ctx.task` set | Spec does not say which message answers which request (no correlation id; 1.1 `elicitationId` proposal closed unmerged) |
| Message to `auth-required` task | Agent SHOULD accept messages; credential normally arrives out-of-band and agent MAY continue without a client message (§7.6.1) | Same as input-required for sends. Blocking call returns a snapshot at auth-required while a background drain continues | Executor must stay alive or resume out-of-band; SDK settles bus but nothing re-drives it (see 4.4) |
| Message to terminal task | `UnsupportedOperationError` (§3.1.1) | `UnsupportedOperationError` (SDK:2547) | none |
| Unknown `taskId` / ctx mismatch | `TaskNotFoundError`; MUST reject mismatching contextId; MUST infer contextId from task | Same (SDK:2533-2560) | none |

| `acceptedOutputModes` | Agents SHOULD tailor output | Parsed only; not used by handler [verified: SDK:301-315 only] | Core must do output-mode filtering itself |

## 3. Details

### 3.1 Operations and objects (spec 1.0.1)

Operations [verified: Spec §3.1, §5.3, proto `service A2AService`]:

| v1.0 operation | v0.3 name | Notes |
|---|---|---|
| `SendMessage` | `message/send` | returns `Task` OR `Message` |
| `SendStreamingMessage` | `message/stream` | first event Task or exactly one Message |
| `GetTask` | `tasks/get` | `historyLength` |
| `ListTasks` | not in 0.3 | cursor pagination, sorted by status timestamp desc, MUST be caller-scoped |
| `CancelTask` | `tasks/cancel` | |
| `SubscribeToTask` | `tasks/resubscribe` | first event MUST be a `Task` snapshot; terminal -> `UnsupportedOperationError` |
| `Create/Get/List/DeleteTaskPushNotificationConfig` | `tasks/pushNotificationConfig/*` | flattened, `task_id` + `id` |
| `GetExtendedAgentCard` | `agent/getAuthenticatedExtendedCard` | gated by `capabilities.extendedAgentCard` |

Changes v0.3 -> v1.0 [verified: https://a2a-protocol.org/latest/whats-new-v1/]: operation renames; `kind` discriminator removed everywhere; `Part` becomes one message with `oneof content {text | raw | url | data}` plus `mediaType`, `filename`, `metadata` (TextPart/FilePart/DataPart gone; `file.fileWithUri` -> `url`, inline bytes -> `raw`, `mimeType` -> `mediaType`); enums become `TASK_STATE_*`, `ROLE_USER|ROLE_AGENT`; `final` removed from `TaskStatusUpdateEvent` (stream closure is the completion signal); `StreamResponse` wrapper `{task|message|statusUpdate|artifactUpdate}`; cursor pagination; `tenant` on all requests; `A2A-Version` and `A2A-Extensions` service parameters; AgentCard `supportedInterfaces[]` replaces `url`/`preferredTransport`; OAuth implicit/password removed, device-code and `pkce_required` added, mTLS scheme added; Agent Card JWS signatures; errors use `google.rpc.Status` + `ErrorInfo` (`domain: "a2a-protocol.org"`); `blocking` replaced by `returnImmediately` (default blocking).

Data model [verified: proto v1.0.1]:
- `Task {id*, context_id, status*, artifacts[], history[], metadata}`
- `TaskStatus {state*, message, timestamp}`; `Message {message_id*, context_id, task_id, role*, parts*, metadata, extensions[], reference_task_ids[]}`
- `Part {content: text|raw|url|data(Value); metadata; filename; media_type}`; `Artifact {artifact_id*, name, description, parts*, metadata, extensions[]}`
- `TaskStatusUpdateEvent {task_id*, context_id*, status*, metadata}`; `TaskArtifactUpdateEvent {task_id*, context_id*, artifact*, append, last_chunk, metadata}`
- Discrepancy: the whats-new page says `extensions[]` was added to the Task object; the v1.0.1 proto has no `extensions` on Task or TaskStatus (only Message, Artifact) [verified: proto]. Treat the proto as normative (spec §1.4 says proto is source of truth).
- `TaskState` (proto numbers): UNSPECIFIED 0, SUBMITTED 1, WORKING 2, COMPLETED 3, FAILED 4, CANCELED 5, INPUT_REQUIRED 6, REJECTED 7, AUTH_REQUIRED 8. There is **no** `unknown` state in v1.0 except `UNSPECIFIED`; `unknown` existed in v0.3 [inferred: v0.3 knowledge; not re-verified online]. Terminal: COMPLETED, FAILED, CANCELED, REJECTED. Interrupted: INPUT_REQUIRED, AUTH_REQUIRED [verified: Spec §3.1.1 and proto comments].
- `ROLE_UNSPECIFIED` and `TASK_STATE_UNSPECIFIED` exist on the wire, so the core union needs an "unspecified/unknown" member [inferred].

Errors [verified: Spec §3.3.2 and JSON-RPC mapping via WebFetch of §5.4]: TaskNotFound -32001, TaskNotCancelable -32002, PushNotificationNotSupported -32003, UnsupportedOperation -32004, ContentTypeNotSupported -32005, InvalidAgentResponse -32006, ExtendedAgentCardNotConfigured -32007, ExtensionSupportRequired -32008, VersionNotSupported -32009; plus standard -32700/-32600/-32601/-32602/-32603. Servers MUST NOT distinguish "not found" from "not authorized" (§3.3.2).

IDs [verified: Spec §3.4]: `taskId` is server-generated; a client-supplied `taskId` MUST reference an existing task else `TaskNotFoundError`; a `contextId` the server cannot accept MUST be rejected (not replaced); mismatching contextId/taskId MUST be rejected; contextId inferred from task when only taskId is given. `contextId` alone starts a new task in an existing conversation. `referenceTaskIds` is a hint that never continues a task (life-of-a-task page).

Idempotency [verified: Spec §3.3.1]: SendMessage MAY be idempotent via `messageId`; CancelTask is idempotent (may later return `TaskNotFound` if purged).

### 3.2 Interactive flows: exact semantics

**input-required.** Agent moves task to `TASK_STATE_INPUT_REQUIRED` with a `TaskStatus.message` explaining what it needs; client "continues the interaction by sending a new message with the same `taskId` and `contextId`" [verified: Spec §3.4.3, example §6.3]. The reply is a plain `SendMessage`; there is no dedicated "answer" operation, no request id, and no schema for the question. State is the only machine-readable signal; the question is free-form `Message.parts` (a data part is allowed: the a2a-samples expense reimbursement agent returns a form as `DataPart` with `input_required` [verified: https://raw.githubusercontent.com/a2aproject/a2a-samples/main/samples/python/agents/adk_expense_reimbursement/agent_executor.py lines 56-67]).

**Does the stream end at input-required?** Normative text in 1.0.1 conflicts:
- §3.1.2/§3.1.6: stream MUST close when task reaches a terminal state; silent on interrupted [verified: Spec 3.1.2, 3.1.6].
- §11.7 (SSE binding): "until the task reaches a terminal **or interrupted** state, at which point the stream closes" [verified: Spec §11.7].
- §3.2.2 blocking SendMessage: returns at terminal OR interrupted [verified].
- 1.1 (`dev-1.1`, PR #2270, merged 2026-10-13, prose only): states are terminal or non-terminal; interrupted states are non-terminal; server MAY keep processing and leave the interrupted state without a client message; entering one SHOULD NOT by itself close a stream; §11.7 "or interrupted" dropped [verified: https://github.com/a2aproject/A2A/pull/2270]. That PR's appendix lists which SDKs close the stream at input-required: a2a-js, a2a-go, a2a-python legacy, a2a-dotnet close; only a2a-python V2 keeps it open [verified: same PR].

**auth-required.** Agent MUST use a Task, MUST transition to `TASK_STATE_AUTH_REQUIRED`, MUST include a status message explaining it unless negotiated elsewhere; credentials SHOULD arrive out-of-band; agent SHOULD keep active response streams open and MAY continue immediately on receipt with no client message; agent SHOULD accept messages to the task while auth-required (to negotiate/reject); entering the state "by itself" is not authorization, and a credential obtained must not be assumed to authorize later messages [verified: Spec §7.6.1-7.6.4]. Issue #1582 (closed) records the difference: input-required needs a follow-up send; auth-required may clear out-of-band, so clients must keep a stream/poll [verified: https://github.com/a2aproject/A2A/issues/1582].

**Message to a WORKING task (steering).** Only normative text: "Agents MAY accept additional messages for tasks in non-terminal states" [verified: Spec §3.3.3]. No state-acceptance table. Epic #1992 states the gap and records two rejected positions: #1027 (accept only in `input-required`, else `UnsupportedOperationError`) and #1022 ("guidable" capability) [verified: https://github.com/a2aproject/A2A/issues/1992]. TSC deliberately kept interrupt semantics out of core. Opt-in extension proposal #2125 (open, 2026-08-11, URI `https://a2a-protocol.org/extensions/steering/v1`): agent card `AgentExtension` with params `interruptible`/`steerable`; client sends normal `message/send` with the `taskId` and `Message.metadata["https://a2a-protocol.org/extensions/steering/v1/control"] = "steer"|"interrupt"`; steer keeps the task `WORKING` and agent MUST reply with a `Task` including the message in history; interrupt moves task to `INPUT_REQUIRED` with task metadata `.../interrupted: true`; unadvertised/unactivated use -> `UnsupportedOperationError -32004` [verified: https://github.com/a2aproject/A2A/issues/2125]. Not accepted into the spec.

**Terminal task.** Further messages -> `UnsupportedOperationError`; "once a task is complete no more messages can be sent to it"; follow-ups start a **new task** in the same `contextId` (optionally `referenceTaskIds` to the earlier one) [verified: Spec §3.1.1; life-of-a-task]. Task revival (#1095) is an open proposal [verified: #1992 body].

**Concurrency.** Multiple concurrent streams per task are allowed and MUST each receive all events in order; closing one MUST NOT affect others; task lifecycle independent of any stream [verified: Spec §3.5.2]. No rule exists on concurrent *sends* to one task, other than idempotency via `messageId`.

**Configuration.** `acceptedOutputModes` (SHOULD tailor output), `historyLength` (unset/0/N), `returnImmediately` (default false -> wait for terminal or interrupted), `taskPushNotificationConfig` (task id empty in SendMessage); `returnImmediately` has no effect on direct Message responses or streaming [verified: Spec §3.2.2, §3.2.4, proto `SendMessageConfiguration`].

### 3.3 Security

- Declared in `AgentCard.securitySchemes` (+ `securityRequirements`): apiKey, http (bearer/basic), oauth2 (authorization_code with `pkce_required`, client_credentials, device_code; implicit/password deprecated), openIdConnect, mutualTLS [verified: proto].
- Server MUST authenticate every request and authorize per task; results MUST be scoped even without filters; auth checks MUST precede any lookup that could leak existence [verified: Spec §7.4, §13.1].
- Extended card requires authentication using a declared scheme; may differ per identity [verified: Spec §13.3].
- Identity reaches the executor: SDK `ServerCallContext.user` (`isAuthenticated`, `userName`), `tenant`, `requestedExtensions`, `state` bag, available as `RequestContext.context` [verified: SDK:2-24, 3384-3430]. The Express adapter calls `userBuilder(req)` per request; the only built-in is `UserBuilder.noAuthentication` [verified: SDK express/index.js:12-14].
- Push: agent MUST put credentials from `authentication` in the webhook request; SHOULD time out (10-30 s recommended; SDK default 5 s), retry with backoff, and block private IPs/localhost (SSRF); receivers MUST validate and respond 2xx [verified: Spec §13.2; SDK:2449-2484].
- `auth-required` is for in-task authorization (OAuth token for a downstream API, or "human approval before a destructive action" as the spec's own example); the spec does not define credential format or scope [verified: Spec §7.6, §7.6.4].

### 3.4 @a2a-js/sdk 1.0.0 server internals (installed)

Citations: `SDK` = node_modules/@a2a-js/sdk/dist/server/index.js.

**RequestContext** fields: `request` (cloned SendMessageRequest incl. configuration/metadata), `taskId`, `contextId`, `context` (ServerCallContext), `task` (loaded existing task or undefined), `referenceTasks`, getter `userMessage` [verified: SDK:2-24].

**Handler flow `sendMessage`** (SDK:2822-2888): require `messageId` -> `isBlocking = returnImmediately !== true` -> new `ResultManager` -> `_createRequestContext` -> optionally save push config -> `eventBusManager.createOrGetByTaskId(taskId)` -> new `ExecutionEventQueue(bus)` -> `_runExecutor` (fire-and-forget `agentExecutor.execute(ctx, bus)`) -> consume queue.
- `_createRequestContext` (SDK:2533-2600): if `message.taskId`: load task (else `TaskNotFoundError`), reject terminal (`UnsupportedOperationError`), reject contextId mismatch (`RequestMalformedError`), **append the incoming message to `task.history` and save it before execution**. New taskId/contextId = uuid when absent. Referenced tasks loaded if present (missing ones only `console.warn`). Required extensions checked here.
- **No check that a previous `execute()` for this task is still running.** A send to a `WORKING` task therefore calls `createOrGetByTaskId` (returns the *existing* bus) and starts a second `execute()` on the same bus; both publish interleaved events; per-task write lock only serializes store writes [verified: SDK:2533-2560 (no in-flight check), 2842; lock SDK:2001-2016]. The fix (a2a-js PR #632, "reject concurrent sendMessage while the task executor is running", throws `UnsupportedOperationError`) is **open, not merged**: `main` handler contains no `executingTaskIds` [verified: https://github.com/a2aproject/a2a-js/pull/632 and grep of main `default_request_handler.ts`].
- `sendMessageStream` (SDK:2890-2930): same setup, then `for await (event of queue.events())` yields mapped StreamResponses; enforces ordering via `_advanceStreamPattern` (first event must be Task or Message; after a Message nothing else; in a Task lifecycle only status/artifact updates) [verified: SDK:3207-3225]. So **every `execute()` call, including follow-up turns, must publish a `task` or `message` event first**, even when `ctx.task` exists [verified: AgentExecutor doc in server/index.d.ts].
- Executor throw: handler synthesizes a Task (if none yet) + `statusUpdate(FAILED)` with text `Agent execution error: ...` [verified: SDK:2675-2720, 2770-2820].

**Event bus / queue lifecycle.**
- `ExecutionEventQueue` subscribes to the bus (`event`, `finished`). `events()` yields until: a `message` event, a statusUpdate with terminal state, **or INPUT_REQUIRED**; AUTH_REQUIRED deliberately not in the stop set. `stop()` unsubscribes [verified: SDK:1602-1660].
- `_settleBus` (SDK:2730-2737) is called in the `finally` of `execute()`: if the last observed state is INPUT_REQUIRED or AUTH_REQUIRED return without closing; otherwise `bus.finished()` + `eventBusManager.cleanupByTaskId` (removes all listeners, deletes bus). Tracking is synchronous via a listener on the bus.
- Consequences [inferred from the code above]: (a) events published after `execute()` returned and the bus was cleaned up reach no listener, so they are neither streamed, nor persisted (the store is only written by `ResultManager`, which is driven by the queue consumer), nor pushed; (b) after `execute()` returns in input-required the original queue has already stopped, so nothing consumes later publishes to the retained bus; the bus stays registered until the next `execute()` settles in a non-interrupted state (a2a-js issue #817 reports a stale-interrupted-event variant that leaks a bus); (c) an executor that returns after publishing auth-required leaves the SSE stream open with no producer, unless something else publishes to that bus later, which is the case the code comment names ("executor resumes publishing after out-of-band credential injection", SDK:1625-1631); a streaming client of such a task hangs until cancel or a later publish [inferred].
- Blocking `sendMessage` at AUTH_REQUIRED: `_processEvents` resolves the caller with a snapshot and `_continueDraining` keeps consuming until terminal [verified: SDK:2847-2853, 2585ff].
- `ResultManager` (SDK:2018-2250): `message` event -> in-memory only; `task` event -> load persisted, merge history/artifacts/metadata, **prepend** latest user message to history if absent, save; `statusUpdate` -> load, overwrite `task.status`, append `status.message` to history (dedup by messageId), save; `artifactUpdate` -> replace or `append` parts by `artifactId`. All store-touching branches run under an in-process promise-chain lock keyed `tenant\0owner\0taskId` [verified: SDK:2001-2016, 2105-2200]. In 1.0.0 a late status update can overwrite a terminal state (blind overwrite, SDK:2150); fixed in 1.2.0 (a2a-js PR #636: terminal states cannot be overwritten with a different state) [verified: https://github.com/a2aproject/a2a-js/pull/636].
- Status messages are appended to history only through status updates; `task` events keep the user message at the front of history [verified: SDK:2105-2140].

**cancelTask** (SDK:2951-3000): load (else `TaskNotFoundError`); CANCELED -> return as is; other terminal -> `TaskNotCancelableError`; **if a bus exists** (live run, or a retained interrupted-state bus) -> `agentExecutor.cancelTask(taskId, bus)` then drain a new queue through a fresh ResultManager; **else** write CANCELED directly and save, executor never called; finally reload and require CANCELED else `TaskNotCancelableError`. Not atomic in 1.0.0; made atomic in 1.2.0 (#636). No bus cleanup happens on this path [inferred: `_settleBus` not called]. Because a bus is retained at input-required, cancelling an interrupted task goes through `executor.cancelTask` even though no `execute()` is running [inferred: bus retention at SDK:2730 + getByTaskId at SDK:2964].

**resubscribe** (SDK:3068-3115): requires `capabilities.streaming`; loads task (not found / terminal -> errors per spec); yields a `Task` snapshot first (spec-conformant); if a bus exists attaches a queue and forwards events for that taskId (so it stops on terminal / input-required just like send streams); if no bus, the stream ends after the snapshot.

**TaskStore interface** [verified: sdk/dist/server/index.d.ts]: `save(task, ctx)` (overwrite by id), `load(taskId, ctx)` (undefined if missing/inaccessible), `list(ListTasksRequest, ctx)` returning `{tasks, nextPageToken, pageSize, totalSize}`. `ctx.tenant`/`ctx.user` are for scoping. No transaction, version/CAS, or lock methods. `InMemoryTaskStore` = Map tenant->owner->taskId with `structuredClone` on read/write, cursor token `base64(timestamp|id)` [verified: SDK:3277-3375]. The only concurrency control is `ResultManager`'s in-process lock, so a multi-instance deployment with a shared durable store has no cross-process serialization [inferred]. Owner key = `user.userName || "unknown"` (SDK:2258-2262). `PushNotificationStore` is a separate interface. DB-backed stores (Kysely: Postgres/MySQL/SQLite/D1, `a2a-db` migration CLI, tenant+owner in primary keys) arrived in SDK 1.3.0 [verified: https://github.com/a2aproject/a2a-js/pull/756].

**Newer SDK behaviour (1.1.0-1.3.0, not installed)** [verified: release notes URL above]: configurable `keepBusAliveStates` (#669, issue #620: executors that return early while work continues elsewhere had buses closed prematurely); `ExecutionEventBusManager.settleByTaskId` seam so a custom/deferred bus owns teardown (#692); terminal-state overwrite guard and atomic cancel (#636); event bus scoped by tenant+owner (1.2.0); media-type validation against `defaultInputModes` (1.2.1, optional); metadata propagation fix for status/artifact events (1.2.1); JSON-RPC errors returned as HTTP 200 and dispatch on `A2A-Version` (1.2.1).

**Versioning.** The SDK validates `A2A-Version` against the card's `supportedInterfaces[].protocolVersion`; an absent header is treated as `0.3` (`ABSENT_HEADER_VERSION`), and a v0.3 compat layer exists under `@a2a-js/sdk/compat/v0_3` [verified: SDK:3384-3395, 3622-3645; dist/compat/v0_3].

### 3.5 Ecosystem practice

- **a2a-samples LangGraph agent**: maps `require_user_input` -> `TaskState.input_required` with a text status message and `final=True`; otherwise `working` updates [verified: https://raw.githubusercontent.com/a2aproject/a2a-samples/main/samples/python/agents/langgraph/app/agent_executor.py lines 50-70]. Question is plain text.
- **a2a-samples expense reimbursement (ADK)**: returns a form as a `DataPart` with `input_required`; sample UI has a `form_render.py` rendering fields (formType: color, date, email, ...) and sends the filled form back as a message [verified: reimb executor lines 56-67; demo/ui/components/form_render.py]. This is a convention of the sample, not a spec schema.
- **Google ADK** (`google/adk-python`): long-running function calls are emitted as `DataPart`s (metadata `adk_type: function_call`, `adk_is_long_running: true`) in a status update with `final=True`; task state is `auth_required` when the function is `adk_request_credential` (EUC), else `input_required`. On the next request, if the task is interrupted and the incoming message has no `function_response` data part, the executor re-emits the same interrupted state with the text "It was not provided a function response for the function call." and does not rerun the agent [verified: https://raw.githubusercontent.com/google/adk-python/main/src/google/adk/a2a/converters/long_running_functions.py lines 90-204; executor_impl.py lines 255-285]. Correlation id = the ADK function-call id carried in data-part content (ADK-specific).
- **a2a-inspector**: sources `ui/src/tasks.ts` and `ui/src/a2a/view.ts` only track and display `taskId`, `contextId`, and the lower-cased state string (including "input-required"); no input-required-specific UI (form, approval buttons) was located in the files read [verified: those files; absence = not found in `tasks.ts`, `view.ts`, `sse.ts`]. Whether its chat input reuses the `taskId` was not verified.

## 4. Gaps and surprises

1. **Spec and SDK disagree on stream-closure at input-required**, and the spec disagrees with itself (§3.1.2 vs §11.7). 1.1 resolves it toward "keep open" but the SDK still closes [verified above].
2. **Sending to a WORKING task is defined as "MAY accept" with no semantics**, and the installed SDK (and `main`) starts a second concurrent executor on the same bus. Nothing in the SDK queues, steers, or rejects. A core that wants deterministic steering must add its own in-flight registry and reject/queue before the SDK handler runs.
3. **The SDK handler assumes one `execute()` call = one turn.** The event bus is torn down (listeners removed) when `execute()` returns unless the last state is input/auth-required. Anything an executor publishes after returning is silently dropped (not stored, not streamed, not pushed).
4. **auth-required keeps the SSE stream open but nothing re-drives it** after `execute()` returns; the SDK relies on the executor resuming publishing out-of-band [verified comment SDK:1625-1631].
5. **No question/answer correlation anywhere in the protocol.** An answer is just the next message to the task. A permission request, a free-text question, and an auth request are all "a status message + state". Multiple simultaneous questions cannot be distinguished (the rejected `elicitationId` proposal addressed this).
6. **Task history is mutated by the SDK before `execute()`**: the user message is appended to the stored task before the executor runs; `ctx.task.history` may or may not already include it (copy semantics: `RequestContext` clones the request, but `task` is the loaded object) [inferred from SDK:2533-2560].
7. **Terminal-state protection and atomic cancel only arrive in SDK 1.2.0.** In 1.0.0 a late status update can resurrect a canceled/completed task (SDK:2150).
8. **`TaskStore` has no CAS/lock**; concurrency control is an in-process map of promise chains, so multiple server instances over one durable store can interleave load-merge-save.
9. **`acceptedOutputModes` is parsed but ignored** by the 1.0.0 handler.
10. **`noAuthentication` user = `UnauthenticatedUser` with `userName ""`**, which the store maps to a shared `"unknown"` owner: all callers share one task namespace in the current core server [verified: SDK:2258-2262; factory.ts:446].
11. Whats-new page claims Task gets `extensions[]`; proto does not [verified].
12. v0.3 had an `unknown` task state; v1.0 has only `TASK_STATE_UNSPECIFIED` [inferred].

## 5. Implications for a provider-neutral core contract

- **Core must own an in-flight run registry and decide what a message to a live (`WORKING`) task means before the SDK sees it.** The SDK default (second concurrent `execute()`) is unsafe; the spec only says "MAY accept". The conformance-matrix default for "provider has no `onMessage`" can legally be either `UnsupportedOperationError` (-32004, matches the proposed-and-rejected #1027 behaviour and the open a2a-js #632 behaviour) or queue-as-next-turn; both are spec-compliant. Pick one and document it; prefer the one that other SDKs converge on (Go has `ErrExecutionInProgress`, Python V2 an `ActiveTaskRegistry` per #632) [verified: PR #632 text].
- **Model input-required/auth-required as pauses within one logical run, not as run termination.** Core's `run.ask` should keep the provider's backend promise pending while the A2A task sits in the interrupted state, and route the next A2A message on that `taskId` to the pending `ask`. If the executor must return after publishing input-required (SDK 1.0.0 behaviour for an `execute()` per turn), core needs the `resume` path from section 6.5 of the design doc; that choice should be made by core, not the provider.
- **Core's own event pipeline should not depend on the SDK bus lifetime.** Wrap `ExecutionEventBus` so that `execute()` stays pending (or core uses `keepBusAliveStates`/`settleByTaskId` once on SDK >= 1.1/1.2) until the run is truly finished; events after teardown are silently lost [verified above]. Bump the SDK floor to at least 1.2.0 for terminal-state guard, atomic cancel, and tenant-scoped buses; 1.3.0 for DB stores [verified: release notes]. A guarded contract test: "publish after execute returns" must be covered.
- **Core `CoreTaskState` should include `unspecified/unknown` and treat unknown values as non-terminal-unknown**; keep legacy names out of providers (matches design doc). Terminal set = completed, failed, canceled, rejected; interrupted set = input-required, auth-required.
- **Interaction wire format is ours to define; the spec gives only state + `TaskStatus.message`.** Evidence of prior art to align with: data part carrying a structured request (a2a-samples reimbursement form; ADK `function_call` data part with `adk_is_long_running`), plus a text rendering. No accepted A2A extension exists, so a `data` part with core-defined schema (namespaced by an extension URI declared on the card, with `A2A-Extensions` negotiation) is the compliant route [verified: Spec §4.6]. Add our own `interactionId` in the data part and require it in the reply data part (text fallback allowed), because the protocol has no correlation id and the `elicitationId` proposal was closed.
- **Distinguish permission/question (input-required) from authorization (auth-required) per spec 7.6**: auth-required SHOULD stay open for out-of-band resolution and MAY resume without a client message; its state transition is not itself an authorization decision and a granted credential must not be assumed to cover later messages (§7.6.4). Core's auto-answer rules for permission asks must be implemented as core policy, never inferred from the state transition.
- **Reply semantics for core**: accept a message to input-required/auth-required as the answer; reject messages to terminal tasks (`UnsupportedOperationError`), mismatched context (`RequestMalformed`), unknown task (`TaskNotFound`); route messages to a `WORKING` task through the steering path. Keep `messageId` dedupe in core (spec allows idempotency by `messageId`).
- **Streaming**: be tolerant: clients may expect either behaviour at input-required. If core stays on SDK 1.0.0 the stream will close at input-required (blocking calls return the snapshot); under the 1.1 prose it SHOULD stay open. Decide and put it in the conformance matrix, and make `SubscribeToTask` the documented way to re-attach after the stream closes (it MUST return a Task snapshot first). Cancel of an interrupted task should end the pending `ask` with `canceled`.
- **Cancel entry point**: the SDK only calls `executor.cancelTask` when a bus exists; with a retained interrupted-state bus it will, otherwise it marks canceled without informing the executor. Core's `abortOrphan` (design §8) is needed exactly in the no-bus branch; test both branches [verified: SDK:2964-3000].
- **Task store**: define core's `TaskStore` with at least load/save/list plus an explicit atomic update primitive (CAS or lock) because the SDK interface has none; persist pending interactions and queued inbox messages there. If core adapts the SDK `TaskStore`, remember the SDK still calls `save`/`load` with `ServerCallContext` and expects tenant+owner scoping.
- **Identity**: `CoreCaller` should be derived from `ServerCallContext.user`/`tenant`; today it is always the unauthenticated user, so per-caller scoping (spec §13.1 MUST) is not yet enforced; interactions need `by: CoreCaller` only once a real `userBuilder` exists.
- **Parts**: v1.0 `Part` is a oneof (text | raw | url | data) with `mediaType`, `filename`, `metadata` on every part, so core's `kind` union should be modeled as content variants + common `{mediaType, filename, meta}` and keep an `unknown` escape (matches design sketch; note `file` in the sketch splits into `raw` and `url`).
- **History**: v1.0 `historyLength` applies to returned copies only; v1.1 replaces history with `timeline` (messages interleaved with status, generation counters). Keep core history as an ordered timeline of `message | status` entries internally so the 1.1 adapter is additive [inferred from dev-1.1 proto].
- **Push**: spec requires auth on webhooks and recommends SSRF filtering; SDK has none. Treat as core-owned policy if push is enabled (the SDK also needs a `pushNotificationStore`).
- **Errors**: use the exact A2A error set listed in 3.1; the SDK exports `TaskNotFoundError`, `TaskNotCancelableError`, `UnsupportedOperationError`, `ContentTypeNotSupportedError`, `PushNotificationNotSupportedError`, `ExtensionSupportRequiredError`, `VersionNotSupportedError`, `InvalidAgentResponseError`, `ExtendedAgentCardNotConfiguredError`, `RequestMalformedError` [verified: sdk/dist/server/index.d.ts line 2], so the adapter can map core errors 1:1.
