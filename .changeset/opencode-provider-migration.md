a2a-opencode is now built on `@a2a-wrapper/core`'s provider contract and no longer depends on `@a2a-js/sdk` (#111, epic #81). Core owns everything A2A (task lifecycle, cancel ordering, queueing, input-required, the persisted context binding); the wrapper only drives an OpenCode server, 1.x or 2.x, behind its existing backend abstraction. Observable A2A behaviour is unchanged (agent card, `message/send` and `message/stream` results, artifact names and chunks, `trace.*` artifacts and lifecycle events with the same usage, intermediate text flushed as status, multi-turn by `contextId`, MCP servers, permission and question auto-handling, config, CLI and env), proved by a golden test against the previous executor (22 recorded scenarios, streamed and blocking, replayed on a 1.x and on a 2.x fake server: 88 comparisons) and by runs against a real OpenCode 2.3.2 server.

## Breaking

- `OpenCodeExecutor`, `SessionManager` and `PermissionHandler` are removed from the public API (`a2a-opencode` and `a2a-opencode/opencode`), with no shim, and so are the `publishStatus`, `publishFinalArtifact`, `publishStreamingChunk` and `publishLastChunkMarker` re-exports (they publish on an SDK event bus, which only core may touch). `OpenCodeProvider` replaces them: it implements `ProviderExecutor` of `@a2a-wrapper/core` (`run`, `steer`, `abort`, `abortOrphan`, `release`, `probeSession`, ...), not the SDK's `AgentExecutor`. Code that called `executor.execute(ctx, bus)` or `cancelTask` must go through the server (or core's `RunRegistry` / `CoreExecutor`).
- `createA2AServer(config)` now takes `(config, { runStore?, eventTransport? })` and returns `{ provider, registry, ... }` (a `ProviderServerHandle`) instead of a handle whose `executor` was an `OpenCodeExecutor`; `handle.executor` is core's executor. `buildContext` is on `handle.provider`. Custom event transports are passed as `{ eventTransport }` (it used to be `executor.customTransport`).
- The package no longer declares `@a2a-js/sdk` (core still lists it as a peer dependency).
- `OpenCodeBackend.sessionPromptAsync` returns the 2.x inbox item the prompt was admitted as and accepts a delivery mode; the backend gained the optional `inboxList` / `inboxCancel`; the 2.x client passes more server events on (`session.execution.started`, the inbox events, `permission.replied`, and how an execution ended on the idle event); `usageRecordFromMessage` moved to `opencode/usage`.

Small, additive differences in what a client sees: the redundant `submitted` status after the initial task snapshot is gone; the completed status now carries `x-usage` (the per-task usage summary the `agent_finished` lifecycle event always had) and `urn:a2a-wrapper:usage:v1`; a failed status carries `code` (`backend`, `unavailable`, `auth`); `agent_started` follows the opening of the session; a canceled or interrupted task closes its lifecycle with one `agent_error`; a task that had a message steered in can carry `x-usage` on a non-final `working` status (read `x-usage` from the completed status). A pending permission request or question of an UNRELATED session is no longer answered by a task (the old start-up poll answered every pending request of the server); those of the sub-sessions OpenCode creates for the task are now routed through `interactions` (asked in `ask` mode, denied when their parent chain cannot be resolved).

## New

- **Resume across turns and restarts**: the OpenCode session id is bound to the `contextId` (`run.bind`, as soon as the session exists, before the first output) and resumed on the next task; a session the server no longer has (`GET` answers not found) starts a fresh one, once. **A restart keeps conversations only with a durable run store** (`createA2AServer(config, { runStore })`); the default store is in memory, so nothing survives a restart until a durable store exists (#69). The system prompt goes into the first message of a session only, also across restarts.
- **Orphaned runs are stopped on the server**: a task that was running when the wrapper died is still being worked on by the OpenCode server. At start-up core now calls `abortOrphan`, which stops the session by id (1.x `abort`, 2.x `interrupt`) and reports `confirmed` only when the server says it is idle. `probeSession` asks the server (`GET` on the session) for core's optional start-up validation.
- **Steering on OpenCode 2.x** (native `delivery: "steer"` and the durable inbox): `steer` answers `inserted` when the server says it delivered the message into the running turn (`session.inbox.delivered`) within `timeouts.steerAck`, otherwise `queued` with the inbox id as the handle, settled later (folded into the turn, started as its own turn, or taken out of the inbox and handed back to core). `interrupt` stops the session's work (`interrupt` without resuming parked messages) and runs the message next; a cancel also empties what the wrapper held in the inbox. OpenCode 1.x has no native steering, so the provider offers no `steer` there and core falls back (queues the message as the next turn and says so).
- **Permissions and questions through the A2A client**: the new `interactions` config section (`mode`, `timeoutMs`, `onTimeout`, `autoAnswer`; `--interactions`, `INTERACTIONS_MODE`). The default (`auto`, no rules) keeps today's behaviour (`features.autoApprovePermissions` / `autoAnswerQuestions`: `always` replies and first-option answers). With `ask`, new sessions ask for edits, shell commands, MCP, fetch and sub-agents (reads stay allowed), permission requests and the `question` tool arrive as `input-required` with the options allow once / always allow / deny, and the task resumes on the reply.
- `timeouts.steerAck` and `session.maxAge` (optional hard maximum age of a session). **`session.ttl` keeps its meaning**: an idle expiry measured from the last use of a context (the other wrappers' `ttl` is a maximum age); `0` disables it; `session.cleanupInterval` still sweeps idle contexts, now by forgetting their binding (the OpenCode session stays on the server, as it always did).
- If the event stream gives up reconnecting, the polling fallback (`features.enablePollingFallback`) now takes over; before, the task waited for the prompt timeout.
