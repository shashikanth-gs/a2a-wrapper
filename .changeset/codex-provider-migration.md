a2a-codex is now built on `@a2a-wrapper/core`'s provider contract and no longer depends on `@a2a-js/sdk` (#111, epic #81), and it finally **resumes Codex threads** (#100). Core owns everything A2A (task lifecycle, cancel ordering, queueing, the per-context lane, the persisted context binding); the wrapper only drives the Codex exec SDK (`@openai/codex-sdk`, which it keeps; not the experimental app-server). Observable A2A behaviour is unchanged (agent card, `message/send` and `message/stream` results, artifact names and chunks, `trace.*` artifacts and lifecycle events for commands, file changes, reasoning and MCP calls, `x-usage` from `turn.completed.usage`, multi-turn by `contextId`, MCP servers, `auto` model resolution, sandbox, approval and network config, CLI and env), proved by a golden test against the previous executor (15 recorded scenarios, streamed and blocking: 30 comparisons) and by runs against the real Codex CLI.

## Breaking

- `CodexExecutor` and `SessionManager` are removed from the public API (`a2a-codex` and `a2a-codex/codex`), with no shim. `CodexProvider` replaces them: it implements `ProviderExecutor` of `@a2a-wrapper/core` (`run`, `abort`, `abortOrphan`, `release`, `probeSession`, ...), not the SDK's `AgentExecutor`. Code that called `executor.execute(ctx, bus)` or `cancelTask` must go through the server (or core's `RunRegistry` / `CoreExecutor`).
- `createA2AServer(config)` now takes `(config, { runStore?, eventTransport? })` and returns `{ provider, registry, ... }` (a `ProviderServerHandle`) instead of a handle whose `executor` was a `CodexExecutor`; `handle.executor` is core's executor. `buildContext` is on `handle.provider`. Custom event transports are passed as `{ eventTransport }` (it used to be `executor.customTransport`).
- The package no longer declares `@a2a-js/sdk` (core still lists it as a peer dependency).

Small differences in what a client sees: the redundant `submitted` status after the initial task snapshot is gone; the completed status also carries core's `urn:a2a-wrapper:usage:v1` next to `x-usage`; a failed status carries `code` (`backend`, `auth`, `rate_limit`, `unavailable`); a turn that ends with an error, a cancel or an interrupt closes its lifecycle with one `agent_error` (`trace.lifecycle`); a stream that reports `turn.failed` now FAILS the task with the turn's error (it used to complete with an empty answer); the response artifact id is `response-<taskId>-<turn>` (it was `response-<taskId>`), so the turns of one task no longer replace each other; `cache_write_input_tokens` of the SDK usage is reported as `cacheWriteTokens` (it was always 0); **`x-usage` of a task on a resumed thread is now what that task spent**. Codex reports `turn.completed.usage` as a running total of the whole thread (measured: 13849, 27721 and 41619 input tokens for three one-call turns), which the old executor published as every task's usage, so a long conversation over-reported more with each turn; core now diffs the readings per thread (and keeps the previous one with the binding, also across restarts).

## New

- **Resume across turns and restarts (#100)**: the Codex thread id is bound to the `contextId` (`run.bind`, on `thread.started`, before any output) and resumed on the next task with `resumeThread(id, options)` instead of starting a new thread; a thread Codex no longer has (`no rollout found for thread id ...`), a ref that is not a thread id, or a resume that starts another thread starts a fresh one once (`session-not-found`, reported before anything is published). **A restart keeps conversations only with a durable run store** (`createA2AServer(config, { runStore })`); the default store is in memory, so nothing survives a restart until a durable store exists (#69). `probeSession` checks the thread's rollout file under `$CODEX_HOME/sessions` for core's optional start-up validation.
- **Queue and interrupt on a running task**: `queue` runs the message as the next turn of the task on the same thread; `interrupt` kills the running CLI process and runs the message next; `steer` is not possible on the exec SDK, so core answers it honestly with `queued` (`steer-unsupported`) and runs it as the next turn. There are still no approvals (the exec SDK has none: approval policy `never`), hence no `interactions` section.
- `session.idleTtl` (optional idle expiry). **`session.ttl` keeps its meaning** (maximum age of a context's thread, `<= 0` never reuses), and `session.cleanupInterval` still sweeps idle contexts, now by forgetting their binding (the thread stays on disk).
